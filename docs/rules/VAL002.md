# VAL002 - Division by Unproven Config, Storage, or Collection Divisors

> **Severity:** Warning · **Family:** semantic · **Engine:** compiler-backed (rustc driver) · **Rule name:** `division-without-zero-guard`

## Description

Integer division by zero panics in Rust, and a panic inside runtime code is
one of the worst failure modes a Substrate chain can have. If the divide sits
in a dispatchable, an attacker who can steer the divisor to zero gets a
guaranteed way to abort block execution; if it sits in a hook such as
`on_initialize`, every block that reaches the zero divisor fails, and the
chain stalls until governance or a runtime upgrade intervenes.

The dangerous divisors are rarely literals — dividing by `2` is fine. The risk
concentrates in values the author does not fully control at the call site:
runtime configuration constants read through the `Get` trait (a
misconfigured runtime can legitimately set them to zero), values loaded from
storage, and collection lengths (`.len()` / `.count()`), which are zero
whenever the collection is empty. Code that divides by these without first
proving them non-zero encodes an assumption about deployment configuration
and chain state that nothing enforces.

VAL002 is implemented exclusively in the rustc driver
(`polkadot-linter-driver`); there is no syn-based source implementation. It
runs on fully type-checked HIR, so it knows whether a `get()` call really
resolves to `frame_support`/`sp_runtime`/`sp_core` `Get::get`, whether a
`.len()` receiver is really a countable collection, and whether a guard on the
same binding dominates the division. The emitted message is: "Resolved
config, storage, or collection divisor lacks a nonzero proof".

## What it detects

- A `/` binary expression whose divisor is one of:
  - a resolved `Get::get()` call from `frame_support`, `sp_runtime`, or
    `sp_core` (i.e. a runtime configuration parameter);
  - a `.len()` or `.count()` call on a type resolved as a countable
    collection;
  - a local binding whose value flows from one of the above (tracked through
    `let` bindings, reassignments, and casts).
- The diagnostic is suppressed when the divisor is proven non-zero on the
  path to the division:
  - the binding is guarded by a dominating non-zero check (e.g.
    `if divisor != 0 { ... }`, or an early return in the `else` branch of a
    zero check);
  - the collection whose length is used was guarded as non-empty;
  - the value comes from a `Get` of a `NonZero*` integer type.
- One report per source line; guards are scoped correctly to `if`/`else`
  branches, so a proof inside a `then` branch does not leak past it.

## What should be avoided

```rust
fn on_initialize(_n: BlockNumberFor<T>) -> Weight {
    let stakers = ActiveStakers::<T>::get();
    let pot = RewardPot::<T>::get();

    // ❌ `stakers.len()` is zero whenever nobody is staking — this panics
    // in a hook and stalls the chain.
    let share = pot / (stakers.len() as u128);

    distribute::<T>(&stakers, share);
    T::WeightInfo::on_initialize(stakers.len() as u32)
}
```

The divisor is a collection length that any state transition (everyone
unstaking) can drive to zero; nothing in the code proves otherwise.

## Best practice

Option 1 — guard the collection before dividing:

```rust
fn on_initialize(_n: BlockNumberFor<T>) -> Weight {
    let stakers = ActiveStakers::<T>::get();
    if stakers.is_empty() {
        return T::DbWeight::get().reads(1);
    }
    // ✅ The non-empty guard proves `stakers.len() > 0`.
    let share = RewardPot::<T>::get() / (stakers.len() as u128);
    distribute::<T>(&stakers, share);
    T::WeightInfo::on_initialize(stakers.len() as u32)
}
```

Option 2 — use checked arithmetic and handle the zero case explicitly:

```rust
let share = pot
    .checked_div(stakers.len() as u128)
    .unwrap_or_default();
```

For configuration constants, either check the value (`ensure!(!period.is_zero(), ...)`)
or make zero unrepresentable by using a `NonZeroU32`-style parameter type.

## Configuration

```toml
[rules.severity]
"VAL002" = "warning"

[rules.enabled]
"VAL002" = false
```

There are no rule-specific configuration keys. As a compiler-backed rule,
VAL002 only produces findings when the project is analysed through the rustc
driver.
