# SEC011 - Unbounded Storage Iteration in Callable Runtime Paths

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `storage-iteration-in-dispatchables`

## Description

Iterating a whole FRAME storage map means one database read per key — and the number of keys is decided by the chain's users, not by the developer. A `StorageMap::iter()` loop that was harmless on a test network with fifty entries becomes a time bomb on mainnet with five million: execution time and proof size grow with state, while the extrinsic's declared weight typically does not. On a parachain the PoV budget makes this even sharper — an oversized iteration can render the block impossible to validate.

The failure modes are all bad. If the weight is understated, an attacker can grow the map cheaply (or simply wait for organic growth) until the dispatchable or hook that iterates it exceeds the block budget, stalling block production or starving other extrinsics — a classic storage-fed denial of service. If the iteration lives in `on_initialize`, the chain executes it every block whether there is room or not.

Storage iteration in a callable runtime path is therefore only acceptable when it is explicitly bounded: take a fixed number of entries per block and continue with a cursor, meter the work against a `WeightMeter`, or redesign the data so iteration is unnecessary (aggregate values maintained on write, or a `BoundedVec`/`BoundedBTreeMap` with a hard size limit).

## What it detects

- Calls to `iter()` or `drain()` on compiler-resolved FRAME storage collections (`StorageMap`, `CountedStorageMap`, `StorageDoubleMap`, `StorageNMap`, …) inside function bodies reachable from runtime entry points — public functions and FRAME trait entry points such as the `Hooks` lifecycle methods and `on_runtime_upgrade`. Reachability follows the local call graph, so iteration hidden in a private helper is still found.
- An iteration is **not** reported when it is immediately bounded with `.take(n)` where `n` is an integer literal, or a local binding the flow analysis can prove holds a literal on every path reaching the call (tracked through `if`/`else`, `match` arms, and reassignments).

## What should be avoided

```rust
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::purge_expired())]
pub fn purge_expired(origin: OriginFor<T>) -> DispatchResult {
    ensure_signed(origin)?;
    let now = <frame_system::Pallet<T>>::block_number();

    // ❌ touches every key in the map — cost grows with chain state
    for (id, deadline) in Listings::<T>::iter() {
        if deadline < now {
            Listings::<T>::remove(id);
        }
    }
    Ok(())
}
```

The extrinsic's weight is a constant, but its real cost is proportional to the number of listings — anyone who inflates the map can push this call (and the block containing it) past the execution and PoV limits.

## Best practice

Option 1 — process a bounded batch per call and let callers resume:

```rust
const MAX_PURGE_PER_CALL: usize = 50;

pub fn purge_expired(origin: OriginFor<T>) -> DispatchResult {
    ensure_signed(origin)?;
    let now = <frame_system::Pallet<T>>::block_number();

    // ✅ at most 50 keys are visited, so the weight is honest
    for (id, deadline) in Listings::<T>::iter().take(MAX_PURGE_PER_CALL) {
        if deadline < now {
            Listings::<T>::remove(id);
        }
    }
    Ok(())
}
```

Option 2 — bound the data structure itself so iteration has a hard ceiling:

```rust
#[pallet::storage]
pub type Listings<T: Config> =
    StorageValue<_, BoundedBTreeMap<ListingId, BlockNumberFor<T>, T::MaxListings>, ValueQuery>;
```

With a `BoundedBTreeMap`, `T::MaxListings` caps the worst case at the type level, and the bound can be benchmarked directly.
