# SEM009 - Redundant contains_key before remove or take

| Severity | Default | Engine | Name |
| --- | --- | --- | --- |
| advisory | on | compiler (needs the driver) | `redundant-contains-key-before-remove` |

## What it finds

An `if` checks a storage map with `contains_key`. Its body then calls
`remove` or `take` on the same item with the same key.

## Why it matters

`remove` does nothing when the key is absent, and `take` returns an
`Option`. The `contains_key` call is an extra storage read. It adds weight and
proof size and changes nothing.

## Example

```rust
// Bad: two storage reads.
if Offers::<T>::contains_key(&who, &item) {
    Offers::<T>::remove(&who, &item);
}
```

```rust
// Good: one storage access.
Offers::<T>::remove(&who, &item);

// Good: when you need to know if the key existed.
let offer = Offers::<T>::take(&who, &item).ok_or(Error::<T>::NoOffer)?;
```

## How to fix

1. Remove the `contains_key` check and call `remove` directly.
2. If you need the old value, call `take` and check the `Option`.

## Limits

- The rule reports a guard only when it has no `else` and its body is one
  cleanup statement. A guard that controls other code can change behavior, so
  the rule does not report it.
- It does not match calls inside closures in the body.

## Configuration

No rule-specific settings. Use `[rules.enabled]` and `[rules.severity]`.
