# SEC006 - Unchecked repatriate_reserved Remaining Balance

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `unchecked-repatriate-reserved`

## Description

`ReservableCurrency::repatriate_reserved` moves reserved funds from one account to another (or into the beneficiary's reserved balance). Its signature hides a subtlety: it is *best-effort*. On success it returns `Ok(remaining)`, where `remaining` is the portion of the requested amount that could **not** be moved because the slashed account did not have that much reserved. `Ok(...)` therefore does not mean "the full amount was transferred" — it means "the call did not error."

Discarding or `?`-propagating that value without inspecting it makes the pallet's bookkeeping diverge from reality. A slashing routine may believe it confiscated a full deposit when it only got part of it; an escrow pallet may release goods after "receiving" a payment that was only partially repatriated. Depending on which side the accounting error lands, either users are silently short-changed or the pallet leaks funds it never actually collected — both are direct funds-at-risk bugs, invisible in tests where the reserve always happens to be sufficient.

The fix is mechanical: bind the returned remainder and act on it — assert it is zero when the pallet's own logic guarantees full coverage, subtract it from the credited amount, or surface an error/event when a shortfall matters.

## What it detects

For every function body, the rustc driver resolves calls to `frame_support`'s `repatriate_reserved` (via the `ReservableCurrency` trait) and reports:

- a call used as a bare statement, so the returned `Result` — and the remaining balance inside it — is discarded (this includes `T::Currency::repatriate_reserved(...)?;`, where `?` unwraps the `Ok(remaining)` and then drops it); message: "Resolved repatriate_reserved return value is discarded";
- a call whose result is bound to a pattern with no bindings (e.g. `let _ = ...`); same message;
- a call whose result *is* bound to a variable, but that variable is never subsequently checked — a binding counts as checked when it flows into `is_zero`, `checked_sub`, `saturating_sub`, `defensive_saturating_sub`, or a comparison/binary expression; message: "Resolved repatriate_reserved remaining balance is never checked".

## What should be avoided

```rust
fn settle_deposit(payer: &T::AccountId, treasury: &T::AccountId, fee: BalanceOf<T>) -> DispatchResult {
    // ❌ Ok(remaining) is unwrapped by `?` and then thrown away
    T::Currency::repatriate_reserved(payer, treasury, fee, BalanceStatus::Free)?;
    TotalCollected::<T>::mutate(|total| *total = total.saturating_add(fee));
    Ok(())
}
```

If `payer` had less than `fee` reserved, the treasury received less than `fee`, but `TotalCollected` still records the full amount — the pallet now believes it holds funds that were never transferred.

## Best practice

Option 1 — account for the shortfall:

```rust
fn settle_deposit(payer: &T::AccountId, treasury: &T::AccountId, fee: BalanceOf<T>) -> DispatchResult {
    let remaining =
        T::Currency::repatriate_reserved(payer, treasury, fee, BalanceStatus::Free)?;
    let collected = fee.saturating_sub(remaining);
    TotalCollected::<T>::mutate(|total| *total = total.saturating_add(collected));
    Ok(())
}
```

Option 2 — require full repatriation when partial payment is unacceptable:

```rust
let remaining =
    T::Currency::repatriate_reserved(payer, treasury, fee, BalanceStatus::Free)?;
ensure!(remaining.is_zero(), Error::<T>::InsufficientReserve);
```

Either way, the on-chain accounting reflects what was actually moved, not what was requested.
