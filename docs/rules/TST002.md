# TST002 - assert_ok! on apply_extrinsic Hides Dispatch Errors

> **Severity:** Error · **Family:** test-smell · **Engine:** source analysis (syn) · **Rule name:** `apply-extrinsic-assert-ok`

## Description

`Executive::apply_extrinsic` (and the equivalent test helpers) returns a nested result: `Result<Result<(), DispatchError>, TransactionValidityError>`. The outer layer answers "was the extrinsic valid and included in the block?"; the inner layer answers "did the dispatched call actually succeed?". An extrinsic that passes signature and validity checks but then fails inside the pallet — insufficient balance, a failed `ensure!`, an arithmetic error — produces `Ok(Err(dispatch_error))`.

`assert_ok!` only inspects the outer `Result`. A test written as `assert_ok!(apply_extrinsic(xt))` therefore passes even when the call itself failed, which is exactly the kind of false confidence that lets regressions ship: the block-building path is green while the business logic silently returns errors on every dispatch. Because this failure mode inverts the meaning of a passing test, the rule defaults to **Error** severity.

The rule authority matrix (`docs/rule-authority-matrix.md`) records TST002's target authority as the rustc bridge: the compiler resolves the called function and its nested `Result` type, and a source-span bridge recovers the authored `assert_ok!` location, so a candidate whose result is not actually nested emits no finding. The syn-based source implementation documented here covers the same authored pattern.

## What it detects

In test files:

- any `assert_ok!(...)` statement macro whose token stream contains `apply_extrinsic`.

## What should be avoided

```rust
#[test]
fn signed_extrinsic_is_applied() {
    new_test_ext().execute_with(|| {
        let xt = sign_extrinsic(alice(), RuntimeCall::Balances(transfer_call()));
        // ❌ passes even if the transfer itself returns a DispatchError
        assert_ok!(Executive::apply_extrinsic(xt));
    });
}
```

The inner `Result<(), DispatchError>` is never examined, so a failing transfer still turns the test green.

## Best practice

```rust
#[test]
fn signed_extrinsic_is_applied() {
    new_test_ext().execute_with(|| {
        let xt = sign_extrinsic(alice(), RuntimeCall::Balances(transfer_call()));
        // ✅ asserts both inclusion and successful dispatch
        assert_eq!(Executive::apply_extrinsic(xt), Ok(Ok(())));
    });
}
```

Comparing against `Ok(Ok(()))` checks both layers: the extrinsic was valid, and the dispatched call succeeded.
