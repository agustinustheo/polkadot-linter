# TST002 - assert_ok! on apply_extrinsic hides dispatch errors

| Severity | Default | Engine | Name |
| --- | --- | --- | --- |
| error | on | syntax | `apply-extrinsic-assert-ok` |

## What it finds

A test calls `assert_ok!` with one argument on an `apply_extrinsic(..)` call.

## Why it matters

`apply_extrinsic` returns `Result<Result<(), DispatchError>, TransactionValidityError>`.
`assert_ok!` checks only the outer `Result`. The test passes when the call fails
with `Ok(Err(dispatch_error))`.

## Example

```rust
// Bad: passes even when the transfer fails.
assert_ok!(Executive::apply_extrinsic(xt));
```

```rust
// Good: checks both results.
assert_eq!(Executive::apply_extrinsic(xt), Ok(Ok(())));
```

## How to fix

Compare the result with `Ok(Ok(()))`. You can also unwrap the outer result
first: `assert_ok!(Executive::apply_extrinsic(xt).unwrap())`.

## Limits

The rule does not report these forms, because they check the inner result:

- `assert_ok!(apply_extrinsic(xt).unwrap())`, `.expect(..)` or `?`.
- `assert_ok!(apply_extrinsic(xt), Ok(()))`.
- `apply_extrinsics` (plural), which returns one `Result`.

## Configuration

The bundled `config/default.toml` sets this rule to `error`. The `[test_smells]`
section sets a severity for the whole `TST` family. A `[rules.severity]` entry
for `TST002` overrides it.
