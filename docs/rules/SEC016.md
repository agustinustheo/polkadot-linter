# SEC016 - Runtime Upgrade Writes Storage Without a StorageVersion Check

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `missing-storage-version-check-in-runtime-upgrade`

## Description

`on_runtime_upgrade` runs exactly once per runtime upgrade — but "per upgrade" is the operative phrase. The same migration code ships in the runtime binary and executes on *every* upgrade until it is removed. If a migration transforms storage unconditionally, the second upgrade that includes it re-applies the transformation to already-migrated data: balances double-converted, encodings re-wrapped, entries deleted twice. Because migrations run before any transaction in the block, the corruption is silent, consensus-critical, and typically only discovered after state has diverged.

The FRAME convention for making migrations idempotent is the `StorageVersion`: the pallet declares an in-code version, the chain records the on-chain version, and the migration runs its writes only when the on-chain version is behind, bumping it afterwards. A migration that writes storage without ever consulting a storage version has no guard against re-execution.

This rule flags exactly that shape: an `on_runtime_upgrade` implementation that performs FRAME storage writes but never reads or compares any storage version. Note that `VersionedMigration` and `UncheckedOnRuntimeUpgrade` exist precisely to factor this guard out — migrations wrapped that way are the recommended remediation.

## What it detects

- An `on_runtime_upgrade` function implementing `frame_support`'s `Hooks` or `OnRuntimeUpgrade` trait (implementations of `UncheckedOnRuntimeUpgrade` are exempt, because `VersionedMigration` supplies the version guard around them), where:
  - the body contains at least one resolved FRAME storage write (`put`, `insert`, `mutate`, `mutate_extant`, `remove`, `kill`, `set`, `append`, `take`, `clear_prefix`, or `translate` on a storage type), and
  - the body contains no resolved storage-version check — no call to `on_chain_storage_version`, `in_code_storage_version`, `current_storage_version`, or any `StorageVersion` method.
- Detection uses resolved compiler types, so version checks and storage writes made through helpers with the same names but unrelated types are classified correctly.

## What should be avoided

```rust
impl<T: Config> Hooks<BlockNumberFor<T>> for Pallet<T> {
    fn on_runtime_upgrade() -> Weight {
        // ❌ runs on EVERY upgrade, not just the first one after deploy
        Values::<T>::translate(|_key, old: OldValue| Some(migrate_value(old)));
        T::DbWeight::get().reads_writes(1, 1)
    }
}
```

The next runtime upgrade that still contains this hook re-runs `migrate_value` over already-migrated entries and corrupts state.

## Best practice

Option 1 — guard with the storage version and bump it:

```rust
fn on_runtime_upgrade() -> Weight {
    let on_chain = Pallet::<T>::on_chain_storage_version();
    if on_chain < 2 {
        Values::<T>::translate(|_key, old: OldValue| Some(migrate_value(old)));
        StorageVersion::new(2).put::<Pallet<T>>(); // ✅ never re-applies
        return T::DbWeight::get().reads_writes(2, 2);
    }
    T::DbWeight::get().reads(1)
}
```

Option 2 — prefer `VersionedMigration`, which supplies the guard, the version bump, and logging for you:

```rust
pub type MigrateV1ToV2<T> = frame_support::migrations::VersionedMigration<
    1, // executes only when the on-chain version is exactly 1
    2, // bumps to 2 afterwards
    unversioned::MigrateV1ToV2<T>, // your UncheckedOnRuntimeUpgrade impl
    Pallet<T>,
    <T as frame_system::Config>::DbWeight,
>;
```

The inner migration stays free of version plumbing, and the wrapper guarantees idempotence; adding logging inside the migration makes re-run and skip decisions observable on upgrade.
