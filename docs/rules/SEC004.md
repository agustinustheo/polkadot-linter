# SEC004 - Non-saturating arithmetic in a weight attribute

| Severity | Default | Engine | Name |
| --- | --- | --- | --- |
| warning | off | compiler (needs the driver) | `unsafe-weight-arithmetic` |

## What it finds

A `#[pallet::weight(...)]` expression uses raw `+` or `*` on an integer or a
`Weight`.

## Why it matters

Fees and block limits use the weight. In a release build, an overflow wraps
and does not stop. A wrapped weight can be very small, so an expensive call
becomes almost free. A saturated weight stays at the maximum, so the
transaction is rejected as overweight.

## Example

```rust
// Bad: `*` and `+` can wrap.
#[pallet::weight(
    T::WeightInfo::store_base() + Weight::from_parts(10_000, 0) * (data.len() as u64)
)]

// Good: the result saturates at the maximum.
#[pallet::weight(
    T::WeightInfo::store_base().saturating_add(
        Weight::from_parts(10_000, 0).saturating_mul(data.len() as u64)
    )
)]
```

## How to fix

1. Use `saturating_add` and `saturating_mul`.
2. If possible, get the formula from a benchmark, for example
   `T::WeightInfo::store(data.len() as u32)`.

## Limits

- Off by default. On 10 third-party parachain repositories, 0 of 4 sampled
  findings needed a fix. All were `+` on constant or benchmark weights that
  cannot overflow (`benchmarks/precision/2026-11-external`).
- `saturating_*` and `checked_*` calls do not trigger the rule.
- The rule reports each line one time.

## Configuration

No rule-specific settings. Use `[rules.enabled]` and `[rules.severity]`.
To enable the rule, set `SEC004 = true` under `[rules.enabled]`.
