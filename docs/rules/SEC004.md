# SEC004 - Non-Saturating Arithmetic in Weight Attributes

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `unsafe-weight-arithmetic`

## Description

The expression inside `#[pallet::weight(...)]` is the runtime's promise about how expensive a call is. Fee calculation, block packing, and the block weight limit all trust it. When that expression uses raw `+` or `*` on integers or `Weight` values, an overflow does not abort in a release-built runtime — it wraps. A weight formula like `base * len` with an attacker-chosen `len` can wrap around to a tiny number, so a call that actually consumes enormous resources is admitted into a block as if it were nearly free.

The consequences compound: blocks can exceed their execution budget and take longer than the slot allows, parachain blocks can blow past their PoV limits, and fees no longer reflect cost, giving attackers a subsidized denial-of-service primitive. This is exactly the failure mode Libro's "Use Safe Arithmetic Operations" chapter warns about — uncontrolled overflow in runtime math can stall the chain — and it is most acute in weight formulas because they run for every transaction, before any dispatch-level checks.

`Weight` and the standard integer types provide saturating alternatives (`saturating_add`, `saturating_mul`) that clamp at the maximum instead of wrapping. In a weight context, saturation is the correct failure mode: an overflowed estimate becomes "maximally expensive," which causes the transaction to be rejected as overweight rather than underpriced.

## What it detects

Inside the source span of any `#[pallet::weight(...)]` attribute, the rustc driver reports:

- binary `+` or `*` expressions whose resolved operand type is a raw integer (`u32`, `u64`, ...) or `Weight` (this also covers `.add(...)`/`.mul(...)` calls, since operator overloads resolve to the same binary operations).

Saturating, checked, and defensive helpers (`saturating_add`, `saturating_mul`, `checked_*`) do not trigger the rule. Each offending line is reported once. The diagnostic message is "Resolved non-saturating arithmetic inside #[pallet::weight(...)]".

## What should be avoided

```rust
#[pallet::call_index(2)]
#[pallet::weight(
    T::WeightInfo::store_base() + Weight::from_parts(10_000, 0) * (data.len() as u64)
)]
pub fn store(origin: OriginFor<T>, data: Vec<u8>) -> DispatchResult {
    // ...
}
```

With a large enough `data.len()`, the multiplication wraps in release builds and the sum can come out near zero — the chain then schedules a very expensive call as if it were almost free.

## Best practice

```rust
#[pallet::call_index(2)]
#[pallet::weight(
    T::WeightInfo::store_base().saturating_add(
        Weight::from_parts(10_000, 0).saturating_mul(data.len() as u64)
    )
)]
pub fn store(origin: OriginFor<T>, data: Vec<u8>) -> DispatchResult {
    // ...
}
```

If the formula overflows, the weight saturates at the maximum and the transaction is rejected as overweight — a safe outcome instead of an underpriced one. Better still, derive the formula from benchmarks (`T::WeightInfo::store(data.len() as u32)`), which generates saturating arithmetic for you.
