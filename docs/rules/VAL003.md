# VAL003 - Storage Writes Before Validation

> **Severity:** Warning · **Family:** semantic · **Engine:** compiler-backed (rustc driver) · **Rule name:** `storage-write-before-validation`

## Description

FRAME dispatch follows a "verify first, write last" discipline. Within a
dispatchable, storage writes performed before an error are rolled back by the
transactional dispatch layer, but that rollback is not free: the runtime has
to buffer overlay changes and discard them, so an extrinsic that writes
eagerly and fails late does strictly more work than one that validates
everything up front. Worse, in contexts that are *not* transactional — hooks
such as `on_initialize`, or code invoked with
`#[pallet::call(... )]` paths that opt out of the default transactional
wrapper — a write followed by a failed check simply persists, leaving the
chain in a state that no validation ever approved.

That half-applied state is the real hazard. A pallet that inserts a record,
then fails an `ensure!` on a later condition, can leave dangling entries that
other extrinsics treat as authoritative: phantom balances, reservations
without owners, or counters that no longer match the maps they count. Bugs of
this shape routinely become fund-safety issues because the inconsistent state
is reachable by other calls.

VAL003 is compiler-backed: the authoritative implementation lives in the
rustc driver (`polkadot-linter-driver`) and operates on type-checked HIR, so
"storage write" means a call actually resolved to a FRAME storage mutation,
not a name that happens to look like one. An earlier syn-based source
implementation of this rule has been retired in favour of the compiler
analysis. The emitted message is: "Resolved FRAME storage write occurs before
a fallible validation edge".

## What it detects

- Within a single function body, a call resolved to a FRAME storage write —
  `put`, `insert`, `mutate`, `remove`, `kill`, or `set` on a FRAME storage
  type — that is followed by a fallible edge: any `?`-desugared expression
  (which includes `ensure!`, `ensure_signed(origin)?`, and every other
  early-return validation).
- The diagnostic points at the first storage write that precedes the fallible
  edge; at most one finding is reported per function body.
- Closure bodies are not traversed as part of the enclosing function, so a
  write inside a `mutate` closure is not conflated with the surrounding
  control flow.

## What should be avoided

```rust
#[pallet::call_index(3)]
#[pallet::weight(T::WeightInfo::register())]
pub fn register(origin: OriginFor<T>, deposit: BalanceOf<T>) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ❌ Write happens first...
    Registrations::<T>::insert(&who, RegistrationInfo::new(deposit));

    // ...and a later validation can still fail the extrinsic.
    ensure!(deposit >= T::MinDeposit::get(), Error::<T>::DepositTooLow);
    T::Currency::reserve(&who, deposit)?;

    Ok(())
}
```

If the deposit check or the reserve fails, the insert must be unwound — and in
a non-transactional context it would not be, leaving a registration that was
never paid for.

## Best practice

```rust
#[pallet::call_index(3)]
#[pallet::weight(T::WeightInfo::register())]
pub fn register(origin: OriginFor<T>, deposit: BalanceOf<T>) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ✅ All fallible steps complete before any storage write.
    ensure!(deposit >= T::MinDeposit::get(), Error::<T>::DepositTooLow);
    T::Currency::reserve(&who, deposit)?;

    Registrations::<T>::insert(&who, RegistrationInfo::new(deposit));
    Ok(())
}
```

Every validation and every fallible external call runs first; the storage
write is the last, infallible step, so no execution path can leave partial
state behind.

## Configuration

```toml
[rules.severity]
"VAL003" = "warning"

[rules.enabled]
"VAL003" = false
```

There are no rule-specific configuration keys. As a compiler-backed rule,
VAL003 only produces findings when the project is analysed through the rustc
driver.
