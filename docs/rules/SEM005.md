# SEM005 - Unparameterised Weight Functions Multiplied by Component Counts

> **Severity:** Warning · **Family:** semantic · **Engine:** source analysis (syn) · **Rule name:** `parameterise-weight-functions`

## Description

Benchmarked weight functions exist to charge each extrinsic for what it will
actually do. When an extrinsic's cost scales with an input — the number of
items in a batch, keys removed, accounts touched — the FRAME benchmarking
framework supports this directly: declare the count as a linear component,
benchmark across its range, and the generated `WeightInfo` function takes the
component as a parameter, `T::WeightInfo::process(n)`.

A common shortcut is to benchmark the operation once for a single item and
scale it by hand: `T::WeightInfo::process().saturating_mul(n)`. This gets the
model wrong in both directions. A benchmarked weight is affine, not purely
linear — it contains a constant term (dispatch overhead, base storage
accesses, event deposit) plus a per-item slope. Multiplying the whole figure
by `n` multiplies the constant overhead `n` times, systematically overcharging
users and wasting block space. Conversely, hand-rolled scaling misses costs
the benchmark machinery would have measured — per-item PoV growth or
superlinear effects — which understates weight and erodes the guarantee that
blocks finish within their execution budget. Underweighted extrinsics are an
open invitation for an adversary to build overweight blocks.

The parameterised form `T::WeightInfo::process(n)` evaluates
`base + slope * n` from regression over real measurements, charging the
constant part exactly once.

## What it detects

- A call to a function on a `WeightInfo` path with no arguments whose result
  is immediately scaled with `.saturating_mul(...)` — i.e.
  `T::WeightInfo::foo().saturating_mul(n)`.
- The pattern is flagged both inside `#[pallet::weight(...)]` attribute
  expressions and in ordinary function bodies (for example, weight
  calculations assembled in helpers or returned from hooks).
- Calls that already pass a parameter (`T::WeightInfo::foo(n)`), or
  multiplications whose receiver is not a zero-argument `WeightInfo` call, do
  not trigger the rule.

## What should be avoided

```rust
#[pallet::call_index(2)]
// ❌ Single-shot benchmark scaled by hand: the constant overhead inside
// `remove_entry()` is charged once per item.
#[pallet::weight(T::WeightInfo::remove_entry().saturating_mul(keys.len() as u64))]
pub fn remove_entries(origin: OriginFor<T>, keys: Vec<KeyOf<T>>) -> DispatchResult {
    ensure_root(origin)?;
    for key in &keys {
        Entries::<T>::remove(key);
    }
    Ok(())
}
```

The multiplied weight is neither the measured cost of removing `n` entries
nor a safe upper bound derived from one — it is a guess assembled from the
wrong pieces.

## Best practice

Benchmark with a linear component and pass it through:

```rust
#[benchmarks]
mod benchmarks {
    #[benchmark]
    fn remove_entries(n: Linear<1, { T::MaxRemovals::get() }>) {
        // setup: insert n entries...
        #[extrinsic_call]
        _(RawOrigin::Root, keys);
    }
}
```

```rust
#[pallet::call_index(2)]
// ✅ The generated function models base cost + per-item cost.
#[pallet::weight(T::WeightInfo::remove_entries(keys.len() as u32))]
pub fn remove_entries(origin: OriginFor<T>, keys: Vec<KeyOf<T>>) -> DispatchResult {
    ensure_root(origin)?;
    for key in &keys {
        Entries::<T>::remove(key);
    }
    Ok(())
}
```

The regression over the `Linear` component captures both the constant term
and the marginal per-item cost, so the charged weight tracks the real worst
case at every input size.
