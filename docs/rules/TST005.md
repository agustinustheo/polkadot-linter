# TST005 - Assertions on Implementation Details

> **Severity:** Advisory · **Family:** test-smell · **Engine:** source analysis (syn) · **Rule name:** `implementation-detail-assertions`

## Description

A good pallet test asserts what the chain's users and other pallets can observe: storage values read through the public API, emitted events, dispatch results, and balances. A brittle test asserts *how* the pallet happens to be built right now: private tuple fields, internal caches, counters, or flags. Those internals are refactoring degrees of freedom — the moment someone reorganises the struct or replaces the counter with a derived value, the test breaks even though the pallet still behaves identically.

Worse than the maintenance cost is the false confidence: a test that checks `ledger.0` or `state.cache` can pass while the behaviour visible to users is wrong, and fail while it is right. In a runtime context, where the meaningful contract is "given this extrinsic, this storage and these events result", implementation-detail assertions measure the wrong thing entirely.

The rule authority matrix (`docs/rule-authority-matrix.md`) keeps TST005 on source analysis permanently: whether an assertion targets an implementation detail is a test-design convention, not a resolved-type property, so a compiler port would be weaker.

## What it detects

In test files:

- `assert!`, `assert_eq!`, `assert_ne!`, or `assert_matches!` statement macros whose arguments match any of the configured internal-field regex patterns. The defaults flag tuple-field access (`.0`), underscore-prefixed fields (`._foo`), and fields named `inner`, `state`, `cache`, `counter`, `buffer`, or `flag`.

## What should be avoided

```rust
#[test]
fn stake_updates_ledger() {
    new_test_ext().execute_with(|| {
        assert_ok!(Staking::stake(RuntimeOrigin::signed(1), 100));
        let ledger = Ledger::<Test>::get(1).unwrap();
        assert_eq!(ledger.0, 100);            // ❌ raw tuple field
        assert_eq!(ledger.state.counter, 1);  // ❌ internal bookkeeping
    });
}
```

Both assertions couple the test to the current struct layout; renaming a field or replacing the counter breaks the test without any behavioural change.

## Best practice

```rust
#[test]
fn stake_updates_ledger() {
    new_test_ext().execute_with(|| {
        assert_ok!(Staking::stake(RuntimeOrigin::signed(1), 100));
        // ✅ observable outcomes: public accessor and emitted event
        assert_eq!(Staking::staked_amount(&1), 100);
        System::assert_last_event(Event::Staked { who: 1, amount: 100 }.into());
    });
}
```

The test now survives any internal refactor that preserves what users of the pallet can actually see.

## Configuration

```toml
[rules.severity]
"TST005" = "advisory"

[rules.enabled]
"TST005" = false

[test_smells]
# Regex patterns treated as internal-field access inside assertions
internal_field_patterns = [
    '\.0\b',
    '\._\w+',
    '\.inner\b',
    '\.state\b',
    '\.cache\b',
    '\.counter\b',
    '\.buffer\b',
    '\.flag\b',
]
```

`internal_field_patterns` is the only `[test_smells]` key this rule reads; tune it to match your project's naming conventions for internal state.
