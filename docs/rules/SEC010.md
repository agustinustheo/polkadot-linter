# SEC010 - Missing Transactional Layer in FRAME Hooks

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `missing-transactional-in-hook`

## Description

Dispatchables get atomicity for free: when a `#[pallet::call]` function returns `Err`, FRAME rolls back every storage change the call made. Lifecycle hooks do not enjoy that safety net. Code running in `on_initialize`, `on_finalize`, `on_idle`, or `on_poll` executes directly against storage — if the hook writes to several storage items and then bails out early on a `?`, the writes that already happened stay committed while the rest never execute.

The result is a partially applied state transition baked into the chain at block boundaries, with no user, no event, and often no log to point at it. A queue whose head was popped but whose counter was never decremented, an account debited without the matching credit — these inconsistencies accumulate silently and tend to surface much later as impossible invariant violations that are very hard to trace back to the block where the hook short-circuited.

The fix is to make the hook's storage mutations atomic: either wrap the fallible section in a storage transaction (`with_storage_layer` / `with_transaction`), annotate the hook with `#[transactional]`, or restructure the hook so that all validation happens before the first write. This rule flags hooks where multiple resolved storage writes precede a fallible edge and no transactional protection is present.

## What it detects

- Implementations of the FRAME `Hooks` trait methods `on_initialize`, `on_finalize`, `on_idle`, and `on_poll` where the body:
  - performs **two or more** resolved FRAME storage writes (`put`, `insert`, `mutate`, `remove`, `kill`, `set` on compiler-resolved FRAME storage types), and
  - contains a fallible edge — a `?` operator — that executes **after** at least one of those writes.
- The hook is exempt when:
  - it carries the `#[transactional]` attribute (detected both in HIR and in the authored source), or
  - the writes and the fallible path occur inside a storage-layer closure (`with_storage_layer` and equivalents), whose changes are rolled back automatically on `Err`.
- The diagnostic is reported on the hook definition and includes the number of resolved storage writes found.

## What should be avoided

```rust
impl<T: Config> Hooks<BlockNumberFor<T>> for Pallet<T> {
    fn on_initialize(_n: BlockNumberFor<T>) -> Weight {
        let _ = (|| -> DispatchResult {
            // ❌ two writes land before the fallible step
            QueueHead::<T>::put(next_head);
            QueueLen::<T>::mutate(|len| *len = len.saturating_sub(1));

            // if this fails, the queue is already half-updated
            Self::settle_item(next_head)?;
            Ok(())
        })();
        T::WeightInfo::on_initialize()
    }
}
```

When `settle_item` fails, `QueueHead` and `QueueLen` keep their new values while settlement never happened — the pallet's bookkeeping and its actual state have permanently diverged.

## Best practice

Option 1 — run the fallible section inside a storage transaction:

```rust
use frame_support::storage::with_storage_layer;

fn on_initialize(_n: BlockNumberFor<T>) -> Weight {
    // ✅ on Err, every write inside the closure is rolled back
    let _ = with_storage_layer::<(), DispatchError, _>(|| {
        QueueHead::<T>::put(next_head);
        QueueLen::<T>::mutate(|len| *len = len.saturating_sub(1));
        Self::settle_item(next_head)?;
        Ok(())
    });
    T::WeightInfo::on_initialize()
}
```

Option 2 — validate first, write last, so no fallible edge follows a write:

```rust
fn on_initialize(_n: BlockNumberFor<T>) -> Weight {
    // ✅ the fallible work happens before any storage mutation
    if let Ok(settled) = Self::prepare_settlement(next_head) {
        QueueHead::<T>::put(settled.next_head);
        QueueLen::<T>::mutate(|len| *len = len.saturating_sub(1));
    }
    T::WeightInfo::on_initialize()
}
```

Either approach guarantees the hook commits all of its writes or none of them.
