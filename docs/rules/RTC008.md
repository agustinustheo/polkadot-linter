# RTC008 - Proxy filter fails open

| Severity | Default | Engine | Name |
| --- | --- | --- | --- |
| warning | on | syntax | `proxy-filter-fails-open` |

## What it finds

A restricted proxy type can move funds or gain more rights than intended. The
rule finds two forms in `impl InstanceFilter<RuntimeCall> for ProxyType`:

1. A `filter` deny-list (`!matches!(..)`) that denies some value-moving pallets
   of the runtime but not all of them.
2. An `is_superset` wildcard `(X, _) => true`, where `X` can add proxies and
   another proxy type allows a call that `X` does not allow.

## Why it matters

A deny-list allows every pallet that it does not name. This includes pallets
added later. Asset Hub Westend's `NonTransfer` denied `Balances` and `Assets`,
but not `ForeignAssets`, `PolkadotXcm`, `Revive` and others
([polkadot-sdk#12771](https://github.com/paritytech/polkadot-sdk/pull/12771)).

`is_superset` controls which proxy types a proxy can add. `(X, _) => true` says
that `X` is a superset of all types. This is safe only if every other type
allows a subset of the calls that `X` allows. If not, an `X` proxy can add a
stronger proxy and use it. On the fellowship Asset Hubs, `NonTransfer` could
add a `Collator` proxy, which allows `CollatorSelection`
([fellows runtimes #1341](https://github.com/polkadot-fellows/runtimes/pull/1341)).

## Example

```rust
// Bad
match self {
    ProxyType::Any => true,
    ProxyType::NonTransfer => !matches!(c, RuntimeCall::Balances { .. } | RuntimeCall::Assets { .. }),
    ProxyType::Collator => matches!(c, RuntimeCall::CollatorSelection { .. }),
}
// in is_superset:
(ProxyType::NonTransfer, _) => true,
```

```rust
// Good
ProxyType::NonTransfer => matches!(c, RuntimeCall::System(..) | RuntimeCall::Session(..) | RuntimeCall::Utility(..)),
// in is_superset:
(ProxyType::NonTransfer, ProxyType::CancelProxy | ProxyType::Governance) => true,
```

## How to fix

1. Write restricted filters as allow-lists (`matches!`).
2. List each superset pair explicitly.
3. Add a test that compares the superset pairs with the filters, as #1341 did.

## How it decides

**Deny-list check.** The rule reads the pallets from `construct_runtime!` or
`#[runtime]`. It selects pallets from value-moving crates: `pallet_balances`,
`pallet_assets` (every instance), `pallet_xcm`, `pallet_revive`,
`pallet_contracts`, `pallet_asset_conversion`, `pallet_psm`, `pallet_uniques`,
`pallet_nfts`, `pallet_nft_fractionalization`, `pallet_vesting`,
`pallet_indices`, `orml_tokens`, `orml_xtokens` and `orml_currencies`. It
reports each of these pallets that the deny-list does not name. Naming one
call of a pallet counts as naming the pallet.

**Superset check.** For an unguarded arm `(X, _) => true`, the rule:

1. Checks that the filter of `X` allows `Proxy::add_proxy`.
2. Takes each other proxy type `Y` that no earlier arm handles.
3. Compares the filters of `X` and `Y` per pallet and per call.
4. Reports `X` if one `Y` allows a call that `X` does not allow.

A `Y` that allows a whole pallet is not covered by an `X` that allows some
calls of it. A deny-list `Y` is not covered by an allow-list `X`. The message
names each `Y` and one call that `X` does not allow.

## Limits

- It does not report allow-lists, `ProxyType::Any => true`, or a wildcard that
  the filters support (for example the relay chains' `NonTransfer`).
- A filter with `_`, bindings, guards or nested patterns is unknown. The rule
  does not report or compare unknown filters.
- It skips deny-lists when it cannot find the runtime's pallets, for example
  when the filter is in a different file from `construct_runtime!`.
- It finds the proxy pallet only by the variant name `RuntimeCall::Proxy`.
- Evidence: the parent commits of #12771 and #1341 give 1 and 3 findings, the
  same issues the fixes changed. The merge commits give 0. Pinned SDK: 7
  findings, all correct (`benchmarks/labels/RTC.tsv`).

Runtime scope: see [Runtime configuration rules](runtime-config.md).

## Configuration

No rule-specific settings. Use `[rules.enabled]` and `[rules.severity]`.
