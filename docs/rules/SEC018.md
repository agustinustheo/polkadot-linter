# SEC018 - Weight Does Not Account for Unbounded Extrinsic Input

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `missing-weight-for-unbounded-input`

## Description

The weight attached to a dispatchable is a promise: "executing this call consumes at most this much block capacity, and the caller pays a fee proportional to it." That promise must hold for the *worst case*, not the typical case. When a dispatchable accepts a `Vec` parameter, its real cost — SCALE decoding, iteration, storage writes — scales with the vector's length. If the `#[pallet::weight(...)]` expression is a constant, the promise is broken: a caller submitting a ten-thousand-element vector pays the same fee as one submitting ten elements.

That mismatch is directly exploitable. Decoding happens before the call body runs, so even an extrinsic that immediately rejects long inputs has already spent unpaid-for block time. At scale, underpriced extrinsics let an attacker fill blocks cheaply, starving legitimate transactions and, on a parachain, pushing PoV production past relay-chain limits. Libro's guidance is the same as FRAME's: benchmark the worst-case scenario and make the weight a function of the input size (with a refund via `DispatchResultWithPostInfo` if the actual cost turns out lower).

This rule flags dispatchables whose weight expression ignores an unbounded input's length, unless the body itself provably rejects oversized inputs before doing any work.

## What it detects

- A public FRAME dispatchable with a `#[pallet::weight(...)]` attribute and a parameter whose resolved type contains an unbounded `Vec` (including nested in generics, tuples, or arrays, and behind type aliases), where:
  - the weight expression never references the parameter's size — no `param.len()`, `param.encoded_size()`, `param.using_encoded(..)`, or `encoded_size(&param)`; and
  - the function body does not *begin* with a terminating length guard (an initial `if` that exits the function when the parameter's length exceeds a literal or literal-bound constant).
- Dispatchables marked `#[deprecated]` are skipped.

## What should be avoided

```rust
#[pallet::call_index(3)]
#[pallet::weight(T::WeightInfo::add_members())] // ❌ flat weight
pub fn add_members(origin: OriginFor<T>, members: Vec<T::AccountId>) -> DispatchResult {
    T::AdminOrigin::ensure_origin(origin)?;
    for member in &members {
        Members::<T>::insert(member, ());
    }
    Ok(())
}
```

Each element causes a storage write, but the fee and the block-capacity accounting are identical for 1 element and 100,000 — callers can consume far more block resources than they pay for.

## Best practice

Option 1 — benchmark against the input length and feed it into the weight:

```rust
#[pallet::call_index(3)]
#[pallet::weight(T::WeightInfo::add_members(members.len() as u32))] // ✅ linear component
pub fn add_members(origin: OriginFor<T>, members: Vec<T::AccountId>) -> DispatchResult {
    T::AdminOrigin::ensure_origin(origin)?;
    ensure!(
        members.len() as u32 <= T::MaxMembersPerCall::get(),
        Error::<T>::TooManyMembers
    );
    for member in &members {
        Members::<T>::insert(member, ());
    }
    Ok(())
}
```

The benchmark should exercise the worst case (the largest accepted `members.len()`), so the generated `WeightInfo::add_members(n)` captures the per-element cost honestly.

Option 2 — make the bound part of the type:

```rust
#[pallet::weight(T::WeightInfo::add_members(T::MaxMembersPerCall::get()))]
pub fn add_members(
    origin: OriginFor<T>,
    members: BoundedVec<T::AccountId, T::MaxMembersPerCall>, // ✅ decoder enforces the cap
) -> DispatchResult {
    // ...
    Ok(())
}
```

With a `BoundedVec` parameter the worst case is a compile-time constant, oversized payloads fail to decode at all, and a fixed worst-case weight is sound (optionally refund the difference via `DispatchResultWithPostInfo`).
