# MOK001 - Excessive Mock Setup in Tests

> **Severity:** Warning · **Family:** mock-usage · **Engine:** source analysis (syn) · **Rule name:** `excessive-mock-setup`

## Description

Pallet tests exist to give confidence that dispatchables behave correctly against real storage, real events, and real arithmetic. When a test spends dozens of lines wiring up mocks, builders, and expectations before making one or two assertions, that confidence is diluted: the test increasingly verifies that the code *interacts with the mocks* in a particular order rather than that it *produces the right outcome*. Such tests are brittle — an internal refactor that preserves behavior still breaks them because the choreography changed — and their sheer setup volume hides what property is actually being tested.

FRAME makes outcome-oriented testing unusually cheap: `new_test_ext()` provides a real in-memory runtime, so a test can dispatch a call, then assert on storage values, emitted events, and returned errors with `assert_ok!`, `assert_noop!`, and `assert_last_event`. Heavy mock scaffolding is therefore usually a sign that either shared setup should be extracted into helper functions, or the test should be restructured to exercise real dependencies through the mock runtime instead of stubbing them.

This rule quantifies the smell per test function: it compares the number of mock/setup lines against the number of assertion lines, and separately counts mockist expectation calls (`expect_*`, `times`, `returning`).

Per the [rule authority matrix](../rule-authority-matrix.md), MOK001 remains a source-analysis rule: the mock/setup-to-assertion ratio is a test-design heuristic over authored structure, and a compiler port would be weaker.

## What it detects

Inside each `#[test]` function in a test file:

- **Excessive ratio:** the count of mock/setup lines divided by the count of assertion lines exceeds `max_mock_ratio` (default `3.0`). Only fires when the test has at least one assertion. Mock lines are calls or method calls whose text matches any configured `mock_patterns` entry (`new_test_ext` scaffolding itself is not counted), plus expectation-style method calls. Assertion lines are `assert!`, `assert_eq!`, `assert_ne!`, `assert_ok!`, `assert_err!`, `assert_noop!`, `assert_matches!`, `assert_last_event`, `assert_has_event`, and `assert*` method calls.
- **Too many expectations:** the number of mock-expectation method calls (`expect_*`, `.times(...)`, `.returning(...)`) exceeds `max_mock_expectations` (default `10`).

## What should be avoided

```rust
#[test]
fn transfer_notifies_listener() {
    let mut listener = MockListener::new();
    listener.expect_on_transfer().times(1).returning(|_| Ok(()));
    let mut oracle = MockOracle::new();
    oracle.expect_price().times(2).returning(|_| 42);
    oracle.expect_decimals().returning(|| 10);
    let mut fees = MockFeeSource::new();
    fees.expect_rate().returning(|| Perbill::from_percent(1));
    let ctx = MockContext::with_mock(listener).with_mock(oracle).with_mock(fees);

    ctx.run(|| {
        let _ = Pallet::<Test>::transfer(RuntimeOrigin::signed(1), 2, 100);
        assert_eq!(ctx.calls(), 1); // ❌ one assertion, verifying interaction counts
    });
}
```

Almost the entire test is mock choreography, and the single assertion checks how the mocks were called rather than what happened to balances or events.

## Best practice

Option 1 — test outcomes against the real mock runtime:

```rust
#[test]
fn transfer_moves_funds_and_emits_event() {
    new_test_ext().execute_with(|| {
        assert_ok!(Pallet::<Test>::transfer(RuntimeOrigin::signed(1), 2, 100));
        assert_eq!(Balances::free_balance(2), 100);
        System::assert_last_event(Event::Transferred { from: 1, to: 2, amount: 100 }.into());
    });
}
```

Option 2 — extract unavoidable setup into a helper so each test states only its scenario:

```rust
fn ext_with_oracle(price: u64) -> sp_io::TestExternalities {
    let mut ext = new_test_ext();
    ext.execute_with(|| OraclePrice::<Test>::put(price));
    ext
}

#[test]
fn transfer_respects_oracle_price() {
    ext_with_oracle(42).execute_with(|| {
        assert_ok!(Pallet::<Test>::transfer(RuntimeOrigin::signed(1), 2, 100));
        assert_eq!(Balances::free_balance(2), 100);
    });
}
```

Both variants assert on observable state, so they survive internal refactors and clearly document the behavior under test.

## Configuration

```toml
[rules.severity]
"MOK001" = "warning"

[rules.enabled]
"MOK001" = false

[mock_usage]
max_mock_ratio = 3.0        # mock/setup lines per assertion line before warning
max_mock_expectations = 10  # expect_*/times/returning calls per test before warning
mock_patterns = [           # substrings identifying mock/setup calls
    "MOCK",
    "Mock",
    "MockBuilder",
    "mock",
    "new_test_ext",
    "with_mock",
]
```
