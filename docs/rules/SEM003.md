# SEM003 - Prefer Reference Iteration Over .iter() in for Loops

> **Severity:** Advisory · **Family:** semantic · **Engine:** source analysis (syn) · **Rule name:** `prefer-ref-iteration`

## Description

Rust offers two equivalent spellings for iterating a collection by reference:
`for item in collection.iter()` and `for item in &collection`. They desugar to
the same code — `&collection` goes through `IntoIterator`, which for standard
collections calls `iter()` internally. This rule enforces the project
convention of writing the reference form in `for` loops.

The `&collection` form states the borrow discipline directly in the loop
header: a leading `&` means shared iteration, `&mut` means mutating iteration,
and a bare value means the loop consumes the collection. That three-way
distinction is exactly the information a reviewer needs when scanning pallet
code for accidental moves or unintended mutation, and the sigil communicates
it more directly than a method name at the end of the expression. It is also
the form idiomatic Rust and the standard library documentation use for plain
`for` loops; `.iter()` earns its keep only when starting an adapter chain
(`.iter().map(...)`), which this rule does not flag.

As an Advisory-severity style rule, this has no runtime, weight, or security
impact — the two forms compile identically.

## What it detects

- A `for` loop whose iterated expression is a direct `.iter()` method call on
  a plain path expression, e.g. `for v in validators.iter() { ... }`.
- Loops over `.iter()` on more complex receivers (field accesses, call
  results), iterator chains such as `.iter().enumerate()`, and `.iter()` used
  outside `for` loops are not flagged.
- Pure test paths are skipped, since test utilities often iterate library
  types (e.g. subxt event collections) that expose a custom `iter()` without
  implementing `IntoIterator` for references.

## What should be avoided

```rust
fn total_locked(locks: &[BalanceLock<BalanceOf<T>>]) -> BalanceOf<T> {
    let mut total = BalanceOf::<T>::zero();
    // ❌ `.iter()` in the loop header where a `&` borrow says the same thing.
    for lock in locks.iter() {
        total = total.saturating_add(lock.amount);
    }
    total
}
```

The `.iter()` call is redundant noise: the loop borrows the slice, and the
project convention expresses that with a `&` sigil instead.

## Best practice

```rust
fn total_locked(locks: &[BalanceLock<BalanceOf<T>>]) -> BalanceOf<T> {
    let mut total = BalanceOf::<T>::zero();
    // ✅ Reference iteration: the borrow is visible in the loop header.
    for lock in &locks[..] {
        total = total.saturating_add(lock.amount);
    }
    total
}
```

For an owned collection the fix is simply `for lock in &locks { ... }` (or
`&mut locks` when mutation is intended).
