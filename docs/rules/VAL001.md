# VAL001 - Heavy Storage Reads Before Cheap Validation

> **Severity:** Warning · **Family:** semantic · **Engine:** source analysis (syn) · **Rule name:** `validation-before-heavy-read`

## Description

On a Substrate chain every storage read has a real cost: it consumes database
weight, and on a parachain it also pulls the value's storage proof into the PoV
(Proof of Validity) that must be shipped to and re-executed by relay-chain
validators. That cost is paid even when the extrinsic ultimately fails. If a
dispatchable performs an expensive `StorageMap::get` or `iter` first and only
afterwards checks a cheap precondition such as `ensure!(amount != 0, ...)`, the
failing path is far more expensive than it needs to be.

This ordering is more than an inefficiency — it is a spam amplifier. An
attacker can submit batches of transactions that are guaranteed to fail the
cheap check, knowing that each one still forces the runtime to perform the
heavy reads before rejecting. Because weight for a failed extrinsic is still
charged against the block, mispriced-but-cheap failures crowd out legitimate
traffic and inflate block fullness for no useful work.

The fix is a simple reorder: run all validations that depend only on call
arguments and origin first, then touch storage. Cheap guards act as a filter
that lets the runtime bail out before paying for database access.

Note on engine authority: the repository's rule-authority-matrix
(`docs/rule-authority-matrix.md`) lists VAL001's current authority as the
**rustc bridge**, backed by resolved FRAME storage reads in authored
dispatchable bodies with a pinned nomination-pools baseline. The syn-based
source analysis described here remains the implementation shipped in the
standard scan.

## What it detects

- Inside a production function (test and benchmark files, `#[cfg(test)]`
  items, and try-runtime-gated items are skipped), a heavy operation matching
  a configurable pattern list — by default FRAME storage accessors such as
  `::get(`, `::try_get(`, `::iter(`, `::iter_prefix(`, `::iter_keys(`,
  `::contains_key(`, `::decode_len(`, `::count(`, the typed
  `StorageValue::get` / `StorageMap::get` / `StorageDoubleMap::get` /
  `StorageNMap::get` / `CountedStorageMap::get` forms, and
  `T::DbWeight::get()` — that is followed later in the same function by a
  cheap validation.
- Cheap validations are also pattern-configurable; the defaults are `ensure!`,
  `ensure_signed`, `ensure_root`, `ensure_none`, and predicate checks such as
  `.is_empty()`, `.is_none()`, `.is_some()`, `.is_zero()`, `== 0`, `!= 0`,
  and `.len()` (predicates only count when consumed by a fallible guard such
  as `ensure!`).
- Validations that reference a binding produced by the heavy read are treated
  as data-dependent and do not trigger the rule — they cannot be moved before
  the read. Likewise, reads inside an `if` condition and guards that appear
  after the read result has already been consumed are excluded.
- A later guard is only reported when it is an independent, argument-only
  precondition that could be hoisted above the read. A guard is skipped when
  any of the following holds (the condition's own cost, the third and fourth
  points, is only inspected for `ensure!` guards):
  - its condition references a storage-derived local in the same function —
    one bound (transitively, through `let`, `if let`, `match`, `for`, aliases
    and closure parameters) from any heavy read, including parameters of
    closures passed to `mutate`/`try_mutate` and friends or chained on a
    storage iterator. Only bindings introduced before the guard and in scope
    at it count: a later `let`, a binding in a closed inner block, or a
    closure parameter outside its closure does not suppress the guard. Each
    local counts with the latest `let` or assignment before the guard, so a
    later assignment or a rebinding to an argument does not suppress it;
  - it references a local (or an alias of one) introduced after the read whose
    value comes from a storage read, a call into pallet or config code, or an
    unanalysed macro (pure arithmetic on arguments still moves with the guard);
  - its condition itself reads storage, or calls a same-crate helper
    (`Self::f`, `Pallet::<T>::f`, or a free function `f(..)`) whose body
    reads storage, directly or through other helpers (followed up to four
    calls deep). Helpers are found
    by name among the functions in the enclosing crate's `src/` tree; pure
    helpers such as `Self::current_timeslice()` are cheap, so their guards
    are still reported;
  - its condition calls config or trait code (`T::..`, `<T as ..>::..`, or a
    helper that does), whose cost the linter cannot see.
    `T::Constant::get()` is still cheap;
  - it sits in a closure that may run zero or many times (`map`, `or_else`,
    `try_for_each`, …) while the read does not, or in a branch (`if`/`else`,
    `match` arm) that excludes the read.
- Reads inside `debug_assert*!` and logging macros are diagnostics, not part
  of the validation order, and are ignored.
- One diagnostic is reported per heavy operation, pointing at the read and the
  later cheap check that should precede it.

## Known limitations

Calls into config or trait code are treated as opaque, and a guard that makes
one is never reported, even when the implementation is cheap. Two SDK guards
are hidden this way: `ensure!(!T::QueuePausedQuery::is_paused(&origin))`
after `BookStateFor::get` in `pallet-message-queue`
(`do_execute_overweight_inner`), and `ensure!(!T::Locker::is_locked(..))`
after `Collection::get` in `pallet-nfts` (`do_transfer`). Both are hoistable
when the configured implementation does not read storage.

Same-crate helpers are matched by bare name across the crate, and if any
function of that name reads storage the call counts as a read, which errs
toward suppressing a guard rather than reporting a false positive.

## What should be avoided

```rust
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::redeem())]
pub fn redeem(origin: OriginFor<T>, amount: BalanceOf<T>) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ❌ Heavy storage read performed first...
    let pool = RewardPools::<T>::get(&who).ok_or(Error::<T>::NoPool)?;

    // ...before a validation that only looks at the call argument.
    ensure!(!amount.is_zero(), Error::<T>::ZeroAmount);

    pool.pay_out(&who, amount)
}
```

A zero-amount call is rejected either way, but only after paying for a full
storage read — weight and PoV space spent on a transaction that was doomed
from its arguments alone.

## Best practice

```rust
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::redeem())]
pub fn redeem(origin: OriginFor<T>, amount: BalanceOf<T>) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ✅ Cheap argument check first: fail before touching storage.
    ensure!(!amount.is_zero(), Error::<T>::ZeroAmount);

    let pool = RewardPools::<T>::get(&who).ok_or(Error::<T>::NoPool)?;
    pool.pay_out(&who, amount)
}
```

All checks that depend only on the origin and call arguments run before the
first storage access, so invalid calls are rejected at minimal cost.

## Configuration

```toml
[rules.severity]
"VAL001" = "warning"

[rules.enabled]
"VAL001" = false
```

The rule reads its pattern lists from the `[validation_order]` section:

```toml
[validation_order]
severity = "warning"
# Function-call patterns treated as expensive operations.
heavy_operations = ["::get(", "::iter(", "::contains_key(", "T::DbWeight::get()"]
# Patterns treated as cheap precondition checks.
cheap_validations = ["ensure!", "ensure_signed", ".is_zero()", "== 0"]
```

`heavy_operations` and `cheap_validations` replace the defaults when set, so
extend the full list rather than listing only your additions.
