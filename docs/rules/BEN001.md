# BEN001 - Weight Function Without a Corresponding Benchmark

> **Severity:** Warning · **Family:** benchmark · **Engine:** source analysis (syn) · **Rule name:** `benchmark-for-weight-function`

## Description

On a Polkadot SDK chain, weights are the currency of block space: every extrinsic pre-declares how much execution time and proof size it will consume, and the chain charges fees and fills blocks based on those declarations. Weights only mean something if they are *measured*. A `WeightInfo` function whose value was guessed, hardcoded, or copy-pasted from another pallet breaks the accounting in one of two directions — Libro rates this a Critical issue in "Use Benchmarking for Accurate Dynamic Weights".

If the declared weight is too low, a block can be filled with extrinsics whose real execution time exceeds the block budget. On a parachain that means missed block times, and in the worst case blocks the relay chain validators cannot validate within their execution window — a chain stall. If the declared weight is too high, users are overcharged and block space is wasted because the chain refuses to include work it could easily perform.

The FRAME benchmarking pipeline exists precisely to close this loop: each `WeightInfo` function is supposed to be generated from a benchmark that measured the real cost on reference hardware. This rule enforces the structural half of that contract — every weight function must trace back to a benchmark.

The rule authority matrix (`docs/rule-authority-matrix.md`) records BEN001's target authority as the rustc bridge, which resolves `WeightInfo` calls from authored weight expressions against compiled benchmark identities (pinned `pallet-assets` baseline). The syn implementation documented here performs the same cross-reference at the source level.

## What it detects

For each `weights.rs` file:

- functions declared in a `trait WeightInfo` or in an `impl ... WeightInfo for ...` block are collected;
- benchmark names are collected from the sibling `benchmarking.rs` (or `benchmarks.rs`) — both `#[benchmark]` functions of the v2 API and entries of the legacy `benchmarks! { ... }` macro;
- a diagnostic is emitted for every weight function with no benchmark of the same name;
- if no benchmarking file exists next to `weights.rs` at all, every weight function is flagged.

## What should be avoided

```rust
// weights.rs — hand-edited, no benchmark backs this number
pub trait WeightInfo {
    fn register_asset() -> Weight;
}

impl<T: frame_system::Config> WeightInfo for SubstrateWeight<T> {
    fn register_asset() -> Weight {
        // ❌ guessed constant, never measured
        Weight::from_parts(10_000_000, 0)
    }
}
```

Nothing ties `register_asset`'s declared cost to its real execution cost; the number will drift further from reality with every code change.

## Best practice

```rust
// benchmarking.rs
#[benchmarks]
mod benchmarks {
    use super::*;

    #[benchmark]
    fn register_asset() {
        let caller: T::AccountId = whitelisted_caller();

        #[extrinsic_call]
        _(RawOrigin::Signed(caller.clone()), Default::default());

        assert!(Assets::<T>::contains_key(AssetId::default()));
    }
}
```

With a matching benchmark in place, `weights.rs` is regenerated by the benchmarking CLI on reference hardware instead of being maintained by hand.
