# SEM004 - Wildcard Imports in Non-Test Code

> **Severity:** Warning · **Family:** semantic · **Engine:** source analysis (syn) · **Rule name:** `no-wildcard-imports`

## Description

A wildcard import (`use some::module::*;`) pulls every public item of a module
into scope without naming any of them. In runtime code this trades a few saved
lines for real review and maintenance costs. First, provenance disappears:
when a pallet uses `ensure_signed`, `Weight`, or an extension trait method,
the reader can no longer tell which crate it came from without tooling — an
uncomfortable position when auditing code that moves funds. Second, glob
imports are fragile across dependency upgrades: when an upstream crate adds a
new public item, it can silently shadow or collide with names already in
scope, turning a routine Polkadot SDK version bump into a pile of ambiguity
errors (or worse, a silent behavior change through trait-method resolution).

Substrate codebases are particularly exposed because preludes are large and
overlapping — `frame_support`, `sp_runtime`, and pallet preludes export
hundreds of items, several with generic names like `Get`, `Config`, or
`Member`. Explicit imports keep each file's dependency surface visible and
make grep-based impact analysis reliable.

Tests are a deliberate exception. Test modules conventionally start with
`use super::*;` and `use crate::mock::*;`, where the glob is the point: the
test wants everything the module under test defines. The rule therefore
applies only to production code.

## What it detects

- A top-level (non-function-local), non-`pub` `use` declaration containing a
  glob (`*`), in production code — including globs nested inside grouped
  imports such as `use frame_support::{traits::*, BoundedVec};`.
- The following are allowed and never flagged:
  - imports in test or benchmark files, and inside `#[cfg(test)]` modules;
  - `use super::*;`, `use crate::*;` (self-crate and parent-module globs), and
    prelude globs such as `use frame_support::pallet_prelude::*;`;
  - re-exports (`pub use ...::*;`), which are an API-design choice rather than
    a local import;
  - `extension.rs` files, where `use crate::*;` is a standard Polkadot SDK
    pattern.

## What should be avoided

```rust
// ❌ Production pallet code importing entire foreign modules.
use frame_support::traits::*;
use sp_runtime::traits::*;

pub fn ed() -> BalanceOf<T> {
    // Which crate did `Get` come from? Both globs export items named
    // `Zero`, `Get`, ... — resolution is invisible at the source level.
    T::ExistentialDeposit::get()
}
```

Two overlapping foreign globs make every unqualified name in the file
ambiguous to a human reader, and any upstream addition can create a real
compiler ambiguity.

## Best practice

```rust
// ✅ Explicit imports name exactly what the file depends on.
use frame_support::traits::{Currency, Get, ReservableCurrency};
use sp_runtime::traits::{Saturating, Zero};

pub fn ed() -> BalanceOf<T> {
    T::ExistentialDeposit::get()
}
```

Designed preludes remain fine where they are intended to be glob-imported:

```rust
// ✅ Also acceptable: an intentional prelude.
use frame_support::pallet_prelude::*;
```
