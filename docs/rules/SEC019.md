# SEC019 - Token imbalance escapes a storage layer

| Severity | Default | Engine | Name |
| --- | --- | --- | --- |
| error | on | compiler (needs the driver) | `imbalance-escapes-transaction` |

## What it finds

A closure that runs in a storage layer moves a token imbalance into a variable
declared outside the closure. The closure can then roll back after the move.

## Why it matters

A storage layer rolls back storage writes when the closure fails. It does not
roll back variables outside the closure. An imbalance changes total issuance
when it is dropped. If the closure fails, the withdrawal is rolled back, but the
outside imbalance is dropped later and still changes issuance. The ledger and
the issuance then disagree.

This caused the October 2026 dotUSD exploit (about $1.38M).
[polkadot-sdk#10384](https://github.com/paritytech/polkadot-sdk/pull/10384)
added the bug and
[#11910](https://github.com/paritytech/polkadot-sdk/pull/11910) fixed it.

## Example

```rust
// Bad: `withdrawn` is outside the storage layer.
let mut withdrawn = AssetsInHolding::new();
Config::TransactionalProcessor::process(|| {
    for asset in assets.inner() {
        let credit = Config::AssetTransactor::withdraw_asset(asset, origin, None)?;
        withdrawn.subsume_assets(credit);
    }
    Ok(())
})?;
self.holding.subsume_assets(withdrawn);
```

If the second asset fails, the first withdrawal is rolled back. Its credit is
still in `withdrawn`, and it burns issuance when it is dropped.

```rust
// Good: `withdrawn` is inside the storage layer.
Config::TransactionalProcessor::process(|| {
    let mut withdrawn = AssetsInHolding::new();
    for asset in assets.inner() {
        withdrawn.subsume_assets(Config::AssetTransactor::withdraw_asset(asset, origin, None)?);
    }
    self.holding.subsume_assets(withdrawn);
    Ok(())
})
```

## How to fix

1. Declare the imbalance inside the closure.
2. Move it out only as the last step before the closure returns `Ok`.

## How it decides

The rule checks closures passed to `with_storage_layer`, `with_transaction*`,
`ProcessTransaction::process` and `XcmExecutor::transactional_process*`. It
skips `impl ProcessTransaction for ()`, because that impl has no storage layer.

It reports an outside variable only when all three conditions are true:

1. **The variable holds an imbalance.** Its type contains `Credit`, `Debt`,
   `PositiveImbalance`, `NegativeImbalance` or `AssetsInHolding`. The closure
   borrows the whole variable mutably.
2. **The closure moves an imbalance into it.** For example, `push(credit)`,
   `subsume_assets(credit)` or `slot = Some(credit)`.
3. **The closure can roll back after the move.** A `?`, a returned `Err(..)` or
   a `TransactionOutcome::Rollback(..)` comes after the move. In a loop, an exit
   in a later iteration also counts. If an unconditional `return` or `break`
   follows the move, only the position of the exit counts.

## Limits

- Measured in November 2026: 1 finding on the pinned SDK (the dotUSD line, fixed
  by #11910). 0 findings on the fellows asset hubs, Hydration and the
  parachain template.
- It does not report moves into struct fields, such as
  `self.holding.subsume_assets(credit)`. The XCM executor saves and restores
  `holding` on rollback, so most of these are correct.
- It does not see an imbalance inside a non-generic wrapper struct.
- It does not see `mem::replace` or `mem::swap`.
- It does not see a closure whose only failure is a tail call that returns
  `Result`.
- It does not follow a closure that is stored in a variable first.

## Configuration

No rule-specific settings. Use `[rules.enabled]` and `[rules.severity]`.
