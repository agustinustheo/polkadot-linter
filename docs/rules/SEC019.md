# SEC019 - Token Imbalance Escapes a Transactional Storage Layer

> **Severity:** Error · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `imbalance-escapes-transaction`
>
> **Off by default.** It catches the dotUSD incident shape (pinned by the SDK benchmark), but pre-merge review reproduced rare false positives: an imbalance moved inside a nested block that is followed by an unconditional loop exit in an enclosing block. Enable with `SEC019 = true` under `[rules.enabled]`, or run `config/all-rules.toml`.

## Description

`with_storage_layer` and the XCM executor's `ProcessTransaction::process` run a closure in a storage layer and roll back every storage write if the closure returns `Err`. `with_transaction` (and `with_transaction_opaque_err`, `with_transaction_unchecked`) roll back when the closure returns `TransactionOutcome::Rollback(..)`; `Commit(Err(..))` keeps the writes. Rollback covers storage only. Values that live outside the closure are not rolled back.

Token imbalances (fungible `Credit`/`Debt`, legacy `PositiveImbalance`/`NegativeImbalance`, and the XCM executor's `AssetsInHolding`, which holds them) write total issuance in their `Drop`. If an imbalance is moved into a variable declared *outside* the closure, it outlives the storage layer. When the closure fails, the withdrawal is rolled back, but the imbalance is dropped afterwards and its `Drop` still decreases (or increases) total issuance. The ledger and the issuance no longer agree.

This is the root cause of the October 2026 dotUSD exploit (about $1.38M). [paritytech/polkadot-sdk#10384](https://github.com/paritytech/polkadot-sdk/pull/10384) changed XCM `WithdrawAsset` to collect withdrawn credits into an outer `let mut withdrawn = AssetsInHolding::new();`. A failing later asset rolled back storage, and the `withdrawn` credits were then dropped outside the layer. [#11910](https://github.com/paritytech/polkadot-sdk/pull/11910) fixed it by declaring the locals inside the closure.

## What it detects

A closure passed directly to a transactional-layer function, resolved by DefId:

- `frame_support` `with_storage_layer` and `with_transaction*`;
- `xcm_executor` `ProcessTransaction::process` and `XcmExecutor::transactional_process*`. A call that statically resolves to `impl ProcessTransaction for ()` is skipped: it runs the closure without a storage layer. A generic `Config::TransactionalProcessor::process` call is checked.

The rule reports an outer local only when all of these hold:

1. **It holds an imbalance.** The closure mutably borrows the whole local (rustc's closure capture analysis), and its type contains, at any generic depth, `frame_support` `fungible`/`fungibles` `Imbalance` (`Credit`, `Debt`), a type or associated type named `PositiveImbalance`/`NegativeImbalance`, or `xcm_executor::AssetsInHolding`.
2. **The closure moves an imbalance into it.** A method call on the local (`withdrawn.subsume_assets(credit)`, `credits.push(credit)`) or an assignment to it (`slot = Some(credit)`) takes a non-reference argument whose type contains an imbalance type.
3. **The closure can roll back after the move.** The rollback path is judged from the closure's return type. A closure returning `Result` needs a `?`, or an `Err(..)` that is `return`ed or is the closure's value (its tail, or a branch of it); a discarded `let _ = Err(..)` does not count. A closure returning `TransactionOutcome` needs `TransactionOutcome::Rollback(..)` in the same position. The exit must start after the move-in ends (`credits.push(withdraw()?)` alone is fine: the `?` fires before the credit is stored), or both must sit in the same loop, where a later iteration's `?` rolls back an earlier move. Exits are looked for only in the closure's own body, not in closures nested inside it.

## What should be avoided

```rust
let mut withdrawn = AssetsInHolding::new(); // ❌ outlives the storage layer
Config::TransactionalProcessor::process(|| {
    for asset in assets.inner() {
        let credit = Config::AssetTransactor::withdraw_asset(asset, origin, None)?;
        withdrawn.subsume_assets(credit);
    }
    Ok(())
})?;
self.holding.subsume_assets(withdrawn);
```

If the second asset fails, the first withdrawal is rolled back, but its credit is already in `withdrawn` and burns issuance when it is dropped.

## Best practice

Declare the imbalance inside the closure. Hand it out only once the closure has succeeded:

```rust
Config::TransactionalProcessor::process(|| {
    let mut withdrawn = AssetsInHolding::new(); // ✅ dropped inside the layer on error
    for asset in assets.inner() {
        withdrawn.subsume_assets(Config::AssetTransactor::withdraw_asset(asset, origin, None)?);
    }
    self.holding.subsume_assets(withdrawn);
    Ok(())
})
```

Moving `withdrawn` into `self.holding` is safe here because it is the closure's last step before `Ok(())`: nothing after it can roll back.

## Precision and scope

Only whole-variable mutable captures of owned imbalances are reported (`Vec<&Credit<..>>` holds none). Read-only captures, captures through a `&mut` parameter, and `move` captures are not reported. Imbalances created and dropped inside the closure are fine. Mutating an outer imbalance without moving a new one into it (`credits.clear()`) is not reported. Closures stored in a variable and passed to the layer later are not followed.

### Known limitations (false negatives)

- **Field escapes.** `self.holding.subsume_assets(credit)` inside the closure is not reported. The XCM executor's `transactional_process*` helpers back up `holding` and `fees` and restore them on rollback, so a field-based check would mostly flag correct code.
- **Non-generic wrapper structs.** A local of a type that stores imbalances in private fields without naming an imbalance type in its own type (`struct Pot { credit: Credit<..> }` used as `let mut pot = Pot::default()`) is not recognized as holding an imbalance.
- **`mem::replace`/`mem::swap`.** Moving an imbalance into an outer local through `core::mem::replace(&mut slot, credit)` is not detected.
- **Implicit error paths.** A closure whose only failure path is a tail call returning `Result` (`|| { withdrawn.subsume_assets(c); fallible() }`) has no `?` or `Err(..)` and is not reported.
