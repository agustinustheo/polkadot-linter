# SEC001 - Unbounded Vec in Extrinsic Parameters

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `unbounded-vec-in-extrinsic`

## Description

Every dispatchable is a public entry point: any account can construct a call with any argument values that decode successfully. When a dispatchable accepts a plain `Vec<T>`, the caller — not the pallet author — decides how large that vector is. The SCALE codec places no upper bound on collection length, so an attacker can submit calls carrying megabytes of data.

On a Substrate chain this is more than a memory concern. Oversized inputs inflate proof-of-validity size on parachains, consume decode and processing time that the declared weight may not account for, and can push blocks over their limits. If the extrinsic's weight is constant while its actual cost scales with input length, an attacker pays a fixed, cheap fee for arbitrarily expensive work — a classic weight-exhaustion denial-of-service vector.

The type system offers a direct fix: `BoundedVec<T, MaxLen>` refuses to decode past its limit, so oversized calls are rejected before the dispatchable body ever runs. This is the pattern Libro's "Unchecked Input Parameters" and "Avoid Unbounded Iteration" chapters recommend: make limits part of the type, so validation cannot be forgotten.

## What it detects

The rustc driver resolves types fully (through type aliases, tuples, and nested generics) and reports each dispatchable parameter that:

- belongs to a **public** function recognized as a FRAME dispatchable (a `#[pallet::call_index]` / `#[pallet::weight]` annotated call), and
- has a resolved type that contains an unbounded `Vec<T>` (including `Vec` nested inside other generics or behind a type alias), and
- is **not** guarded by an immediate, terminating length check at the top of the function body (e.g. an early `ensure!`/`if ... return` that rejects oversized vectors against a literal bound), and
- is not in a dispatchable whose body starts with a privileged-origin guard such as `ensure_root(origin)?` or an `EnsureOrigin` check against a named privileged origin (root-only calls are not attacker-reachable in the same way).

The diagnostic message is "Public callable accepts an unbounded Vec parameter after type resolution".

## What should be avoided

```rust
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::submit_scores())]
pub fn submit_scores(origin: OriginFor<T>, scores: Vec<u32>) -> DispatchResult {
    let who = ensure_signed(origin)?;
    for score in &scores {
        Self::record(&who, *score)?;
    }
    Ok(())
}
```

Any signed account can submit millions of entries in `scores`; the constant weight never charges for them, so the loop runs far past what the block budget assumed.

## Best practice

Option 1 — bound the type (preferred):

```rust
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::submit_scores(scores.len() as u32))]
pub fn submit_scores(
    origin: OriginFor<T>,
    scores: BoundedVec<u32, T::MaxScores>,
) -> DispatchResult {
    let who = ensure_signed(origin)?;
    for score in &scores {
        Self::record(&who, *score)?;
    }
    Ok(())
}
```

Option 2 — reject oversized input before doing any work:

```rust
pub fn submit_scores(origin: OriginFor<T>, scores: Vec<u32>) -> DispatchResult {
    ensure!(scores.len() <= 100, Error::<T>::TooManyScores);
    // ...
}
```

`BoundedVec` is stronger: the limit is enforced at decode time and is visible in the call's metadata, so oversized calls never reach dispatch.
