# SEC013 - Unbounded Collections in Storage Items

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `unbounded-storage-collections`

## Description

On a Substrate chain, every storage item contributes to the state trie, and on a parachain it also contributes to the Proof-of-Validity (PoV) that must be shipped to and verified by the relay chain. A storage value whose encoded size has no static upper bound — a `Vec`, `BTreeMap`, `BTreeSet`, or `VecDeque` — can grow with every extrinsic that appends to it. Nothing in the type system stops it from growing forever.

Unchecked growth has compounding consequences: reads and writes of the value become more expensive than the benchmarked weight assumed, PoV size creeps toward the relay-chain limit, and in the worst case a single oversized value makes the block that touches it impossible to produce or validate — effectively bricking the functionality that depends on it. An attacker who can influence the collection (for example by registering entries via a cheap extrinsic) can accelerate this deliberately.

FRAME acknowledges this risk in its macro design: a `#[pallet::storage]` item whose value type is not statically bounded must either use a bounded container or carry an explicit `#[pallet::unbounded]` opt-out. This rule flags storage items that smuggle an unbounded collection into storage without that explicit acknowledgement, so the decision to allow unbounded growth is always visible and reviewable.

## What it detects

- A `#[pallet::storage]` type alias (for `StorageValue`, `StorageMap`, `CountedStorageMap`, `StorageDoubleMap`, or `StorageNMap`) whose resolved **value** type contains an unbounded collection: `Vec`, `VecDeque`, `BTreeMap`, or `BTreeSet`.
- The check is performed on fully resolved compiler types, so the unbounded collection is found even when it is nested inside a struct's generic arguments, a tuple, an array, or hidden behind a chain of type aliases.
- Storage items annotated with `#[pallet::unbounded]` are not flagged — the opt-out is treated as a deliberate, documented decision.
- Bounded containers (`BoundedVec`, `WeakBoundedVec`, `BoundedBTreeMap`, `BoundedBTreeSet`) never trigger the rule.

## What should be avoided

```rust
#[pallet::storage]
pub type ActiveProposals<T: Config> = StorageValue<
    _,
    Vec<Proposal<T::AccountId>>, // ❌ grows without limit
    ValueQuery,
>;
```

Every submitted proposal makes this single value larger; the weight charged for reading it stays flat while the real cost grows, and eventually decoding the value can exceed block limits.

## Best practice

Option 1 — use a bounded container with a configurable limit:

```rust
#[pallet::config]
pub trait Config: frame_system::Config {
    /// Maximum number of proposals that can be active at once.
    #[pallet::constant]
    type MaxActiveProposals: Get<u32>;
}

#[pallet::storage]
pub type ActiveProposals<T: Config> = StorageValue<
    _,
    BoundedVec<Proposal<T::AccountId>, T::MaxActiveProposals>, // ✅ statically bounded
    ValueQuery,
>;
```

Making the bound a `Config` constant (rather than a hardcoded number) lets each runtime tune the limit without touching pallet logic. Inserting past the limit now returns an error the pallet must handle, which forces growth to be an explicit design decision.

Option 2 — if unbounded growth is genuinely required, opt out explicitly:

```rust
#[pallet::storage]
#[pallet::unbounded] // ✅ documented, reviewable decision
pub type MigrationQueue<T: Config> = StorageValue<_, Vec<AccountIdOf<T>>, ValueQuery>;
```

The attribute keeps the metadata honest and makes the unbounded item stand out in review; pair it with an operational story for how growth is limited in practice.
