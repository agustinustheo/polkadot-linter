# BEN002 - Benchmark Without Verification Block

> **Severity:** Warning · **Family:** benchmark · **Engine:** source analysis (syn) · **Rule name:** `benchmark-verification`

## Description

A benchmark that measures the wrong thing is worse than no benchmark, because its output looks authoritative. The classic failure is the silent no-op: the benchmark's setup is subtly wrong — a missing origin, an unfunded account, an absent storage precondition — so the measured call bails out early through a cheap error path. The recorded weight is then a fraction of the real cost, `weights.rs` gets regenerated with that number, and every block can now be overfilled with underpriced extrinsics. On a parachain that is a route to blocks that exceed their execution budget.

The defence built into the FRAME benchmarking framework is verification: after the measured call, assert that the expected state change actually happened. In the legacy `benchmarks!` macro this is the `verify { ... }` section; in the v2 `#[benchmark]` API it is simply assertions placed after the `#[extrinsic_call]` / `#[block]` section. If the call was a no-op, the verification fails and the bogus measurement never reaches `weights.rs`.

This rule requires every benchmark to contain some form of postcondition check.

The rule authority matrix (`docs/rule-authority-matrix.md`) deliberately keeps BEN002 on source analysis: the authored `verify` block and its position outside the measured block are consumed by the FRAME benchmark macro, so expanded HIR cannot prove this authored verification contract — the source is the authority.

## What it detects

In benchmark files, for each benchmark (v2 `#[benchmark]` functions and entries of the legacy `benchmarks! { ... }` macro), the rule flags the benchmark when its body — excluding code inside `#[block]` sections, which is the measured code, and ignoring string literals and line comments — contains none of:

- a `verify` block (`verify { ... }`);
- a call matching one of the configured `verification_patterns` (by default `verify`, `assert_last_event`, `assert_has_event`);
- a standard assertion: `assert!`, `assert_eq!`, `assert_ne!`, `assert_ok!`, `assert_noop!`, `assert_err!`, `ensure!`, `assert_last_event(`, or `assert_has_event(`.

## What should be avoided

```rust
#[benchmark]
fn claim_reward() {
    let caller: T::AccountId = whitelisted_caller();

    #[extrinsic_call]
    _(RawOrigin::Signed(caller));
    // ❌ no postcondition: if claim_reward exits early on
    //    `NothingToClaim`, the "measured" weight is a no-op's cost
}
```

If the setup forgot to create a pending reward, the benchmark quietly measures the cheap error path and the generated weight underprices every real claim.

## Best practice

```rust
#[benchmark]
fn claim_reward() {
    let caller: T::AccountId = whitelisted_caller();
    PendingRewards::<T>::insert(&caller, 100u32.into());

    #[extrinsic_call]
    _(RawOrigin::Signed(caller.clone()));

    // ✅ prove the measured call really did the work
    assert!(PendingRewards::<T>::get(&caller).is_none());
    assert_last_event::<T>(Event::RewardClaimed { who: caller, amount: 100u32.into() }.into());
}
```

The assertions after the measured call guarantee the benchmark exercised the full success path before its timing is trusted.

## Configuration

```toml
[rules.severity]
"BEN002" = "warning"

[rules.enabled]
"BEN002" = false

[benchmarking]
# Function/block names accepted as benchmark verification
verification_patterns = ["verify", "assert_last_event", "assert_has_event"]
```

`verification_patterns` is the only `[benchmarking]` key this rule reads; add your project's custom assertion helpers (e.g. `assert_state`) so they count as verification.
