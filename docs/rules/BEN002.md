# BEN002 - Benchmark Without Verification Block

> **Severity:** Warning · **Family:** benchmark · **Engine:** source analysis (syn) · **Rule name:** `benchmark-verification`

## Description

A benchmark that measures the wrong thing is worse than no benchmark, because its output looks authoritative. The classic failure is the silent no-op: the benchmark's setup is subtly wrong — a missing origin, an unfunded account, an absent storage precondition — so the measured call bails out early through a cheap error path. The recorded weight is then a fraction of the real cost, `weights.rs` gets regenerated with that number, and every block can now be overfilled with underpriced extrinsics. On a parachain that is a route to blocks that exceed their execution budget.

The defence built into the FRAME benchmarking framework is verification: after the measured call, assert that the expected state change actually happened. In the legacy `benchmarks!` macro this is the `verify { ... }` section; in the v2 `#[benchmark]` API it is assertions placed after the `#[extrinsic_call]` / `#[block]` section, or, inside a measured `#[block]`, assertions that wrap or follow the measured call. If the call was a no-op, the verification fails and the bogus measurement never reaches `weights.rs`.

This rule requires every benchmark to contain some form of postcondition check.

The rule authority matrix (`docs/rule-authority-matrix.md`) deliberately keeps BEN002 on source analysis: the authored `verify` block and assertion placement are consumed by the FRAME benchmark macro, so expanded HIR cannot prove this authored verification contract — the source is the authority.

## What it detects

For each actual v2 `#[benchmark]` function or v1 benchmark macro entry, the rule reports a benchmark with no verification after its measured call/block. The v2 module attributes `#[benchmarks(...)]` and `#[instance_benchmarks(...)]` do not turn helper functions into benchmarks.

V2 function bodies are parsed with `syn`, so multiline signatures, const generic expressions, nested blocks, and turbofish helper arguments do not truncate the body. Statements after the measured `#[extrinsic_call]` or `#[block]` count as postconditions. Inside a measured `#[block]` (as in the pov benchmarks), the statements after the first one that calls the owning pallet (`Pallet::f(..)`, `Self::f(..)`, `crate::Pallet::f(..)`, `<Pallet<T>>::f(..)`, a local alias of these, or a bound `Call` dispatch) count too, as does that statement itself when it contains an assertion (`assert_ok!(Pallet::<T>::f(..))`, also inside a loop); assertions before the measured call are preconditions and do not count. A `#[block]` with no pallet call counts when every one of its statements asserts (pov storage-read benchmarks such as `assert_eq!(Map::<T>::get(k), v)`); a loop, closure or `let` with a body counts only if its body asserts in every statement too. A v1 measured block (`}: { .. }`) is read the same way as a v2 `#[block]`; otherwise only a nonempty separate `verify { ... }` section counts, and empty or comment-only blocks are insufficient. Assertions in setup code are insufficient. A benchmark whose measured block is empty (`#[block] {}`) and which returns `Err(BenchmarkError::Override(..))` sets its weight by hand and is not reported. For an authored v2 function without a measurement marker, its body is checked for verification.

Accepted verification includes:

- a nonempty v1 `verify` section;
- calls/macros matching configured `verification_patterns`, including qualified helpers and `assert_last_event::<T>(...)`;
- standard `assert!`, `assert_eq!`, `assert_ne!`, `assert_ok!`, `assert_noop!`, `assert_err!`, `assert_matches!`, and `ensure!` checks, and `verify(..)`, `assert_last_event(..)` and `assert_has_event(..)` calls, even when not configured.

A name counts when followed by `!`, `(`, `::` or another delimited group, so a bare identifier such as a variable named `verify` does not.

The rule examines benchmark definitions in any Rust source file, including inline modules and external benchmark crates. Comments, string contents, rustdoc examples, test-only modules, test files/targets, and actual Cargo example/bench targets do not count. FRAME example library crates remain in scope. In Cargo crates, only files reachable through declared production/runtime-benchmark modules are analyzed. Runtime-benchmark feature gates are retained. Presence of an assertion is a structural signal; this check does not prove its logical strength.

## Not reported

- A measured block (v2 `#[block]` or v1 `}: { .. }`) whose measured statement applies `?`, `.expect(..)` or `.unwrap()` directly to its expression: `Pallet::<T>::f(..)?;` or `let r = Pallet::<T>::f(..).expect(..);`. The measured statement is the first one that calls the owning pallet or, when none does, the block's first statement. A failing call aborts the benchmark, so the cheap error path is never recorded. A check on another statement does not count: `let x = Foo::<T>::get().unwrap(); let _ = Pallet::<T>::f(x);` is reported.
- A measured block whose first statement binds a result that a later assertion names (`let r = other::Pallet::<T>::f(..); assert_ok!(r);`), for calls the pallet-call matching does not recognise. An assertion on a value derived from the binding (`let len = r.count(); assert_eq!(len, n)`) does not count.
- Hook benchmarks: a name containing `on_initialize`, `on_finalize`, `on_idle` or `on_runtime_upgrade`. This skip is based on 2 audited samples (Acala idle-scheduler and homa `on_initialize`), where nothing observable existed to assert.
- Benchmarks that return `Err(BenchmarkError::Override(..))` from an empty measured block.

## What should be avoided

```rust
#[benchmark]
fn claim_reward() {
    let caller: T::AccountId = whitelisted_caller();

    #[extrinsic_call]
    _(RawOrigin::Signed(caller));
    // ❌ no postcondition: if claim_reward exits early on
    //    `NothingToClaim`, the "measured" weight is a no-op's cost
}
```

If the setup forgot to create a pending reward, the benchmark quietly measures the cheap error path and the generated weight underprices every real claim.

## Best practice

```rust
#[benchmark]
fn claim_reward() {
    let caller: T::AccountId = whitelisted_caller();
    PendingRewards::<T>::insert(&caller, 100u32.into());

    #[extrinsic_call]
    _(RawOrigin::Signed(caller.clone()));

    // ✅ prove the measured call really did the work
    assert!(PendingRewards::<T>::get(&caller).is_none());
    assert_last_event::<T>(Event::RewardClaimed { who: caller, amount: 100u32.into() }.into());
}
```

The assertions after the measured call guarantee the benchmark exercised the full success path before its timing is trusted.

## Configuration

```toml
[rules.severity]
"BEN002" = "warning"

[rules.enabled]
"BEN002" = false

[benchmarking]
# Function/block names accepted as benchmark verification
verification_patterns = ["verify", "assert_last_event", "assert_has_event"]
```

`verification_patterns` is the only `[benchmarking]` key this rule reads; add your project's custom assertion helpers (e.g. `assert_state`) so they count as verification.
