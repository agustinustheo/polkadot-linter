# SEC005 - Expensive Operations in Weight Calculation

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `expensive-weight-calculation`

## Description

The `#[pallet::weight(...)]` expression is evaluated *before* dispatch, during transaction validation and fee calculation — for every transaction that names the call, including ones that will ultimately fail signature or nonce checks. Crucially, this evaluation itself is not metered: no fee has been charged yet, and the computed weight does not account for the cost of computing the weight.

Putting real work inside that expression therefore creates free, attacker-triggerable computation. A storage read in a weight formula hits the database (and on a parachain, drags the read into the PoV) once per candidate transaction; encoding or recursively inspecting a wrapped call (`call.get_dispatch_info()`, `call.encode()`) scales with attacker-supplied call size. Flooding the transaction pool with such calls makes every node repeatedly perform this unpaid work during validation — a denial-of-service vector that never even needs a transaction to be included in a block.

Weight expressions should be cheap, pure functions of the call's arguments: benchmark-derived `WeightInfo` methods parameterized by lengths and counts. Anything that depends on state belongs in the dispatch logic, with the difference refunded via `DispatchResultWithPostInfo` if the actual cost turns out lower than the declared worst case.

## What it detects

Inside the source span of any `#[pallet::weight(...)]` attribute, the rustc driver reports (once per line):

- FRAME storage reads — resolved `get` calls on FRAME storage types (`StorageValue`, `StorageMap`, and friends);
- resolved calls to `get_dispatch_info` (recursively computes the inner call's dispatch info);
- resolved calls to SCALE codec operations: `encode`, `using_encoded`, or `decode`.

The diagnostic message is "Resolved expensive operation inside #[pallet::weight(...)]".

## What should be avoided

```rust
#[pallet::call_index(4)]
#[pallet::weight({
    let members = Members::<T>::get().len() as u64; // storage read, pre-dispatch
    T::WeightInfo::notify_base().saturating_mul(members)
})]
pub fn notify_members(origin: OriginFor<T>, note: BoundedVec<u8, T::MaxNote>) -> DispatchResult {
    // ...
}
```

Every transaction in the pool triggers an unpaid database read just to be *validated*; an attacker can submit thousands of such transactions and never pay for any of the reads.

## Best practice

Charge the benchmarked worst case up front, then refund the actual cost from inside the dispatchable, where execution is paid for:

```rust
#[pallet::call_index(4)]
#[pallet::weight(T::WeightInfo::notify_members(T::MaxMembers::get()))]
pub fn notify_members(
    origin: OriginFor<T>,
    note: BoundedVec<u8, T::MaxNote>,
) -> DispatchResultWithPostInfo {
    ensure_signed(origin)?;
    let members = Members::<T>::get();
    // ... do the work ...
    Ok(Some(T::WeightInfo::notify_members(members.len() as u32)).into())
}
```

The weight expression is now a constant-time function of a configuration bound, and the state-dependent cost is settled post-dispatch with a refund.
