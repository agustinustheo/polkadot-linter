# SEC024 - Discarded Funds in an Error

> **Severity:** Error · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `discarded-funds-in-error`

> **Off by default.** The mechanism is real, but on real code most findings are deliberate "pay the author or burn" handlers, many with a comment saying so (see [Measurement](#measurement)). Enable with `SEC024 = true` under `[rules.enabled]`, or run `config/all-rules.toml`.

## Description

`fungible::Balanced::resolve(who, credit)` returns `Result<(), Credit>`. When the deposit fails (the account is below the existential deposit, frozen, or does not exist), the credit comes back in `Err`. If that `Result` is discarded, the `Credit` is dropped, and its `OnDrop` handler adjusts total issuance: the funds are burned silently. `settle` returns the `Debt` in `Err` the same way, and dropping a `Debt` mints.

The 2026-11 precision audit labeled two Astar runtime findings true positives for this reason ([benchmark labels](../../benchmarks/precision/2026-11-run-audit/labels.tsv) C006 and C012, Astar `02b78d7`):

```rust
impl OnUnbalanced<Credit<AccountId, Balances>> for CollatorRewardPot {
    fn on_nonzero_unbalanced(amount: Credit<AccountId, Balances>) {
        let staking_pot = PotId::get().into_account_truncating();
        let _ = Balances::resolve(&staking_pot, amount); // runtime/astar/src/lib.rs:638
    }
}
```

and `let _ = Balances::resolve(&TreasuryPalletId::get().into_account_truncating(), reward);` in the inflation payout (`runtime/astar/src/lib.rs:484`). If the pot or treasury account cannot receive the credit, the reward is burned and nothing reports it. SEC007 caught them only because it flags every `let _ =`; SEC024 flags them because of the type that is dropped.

No upstream fix PR exists to use as an oracle pair: a search of polkadot-sdk history and PRs found none.

## What it detects

A call whose typeck result is `Result<_, E>` where `E` owns a value whose `Drop` writes total issuance (the same types SEC019 tracks): fungible/fungibles `Imbalance` (`Credit`, `Debt`), the legacy `NegativeImbalance`/`PositiveImbalance` (also as associated types, e.g. `Currency::resolve_into_existing`), or xcm-executor `AssetsInHolding`. Generic arguments of `E` count too; references do not.

The `Result` is discarded when it is used as a statement, bound to `let _ = ..` or to an `_`-prefixed name that is never used, after any of `.ok()`, `.err()`, `.map(..)`, `.is_ok()`, `.is_err()`.

The rule checks closure bodies too. Code compiled only for tests or benchmarks is skipped (as for SEC022).

## What should be avoided

```rust
let _ = T::Currency::resolve(&pot, credit); // ❌ credit burned if `pot` cannot receive it
T::Currency::resolve(&pot, credit).ok();    // ❌
```

## Best practice

```rust
if let Err(credit) = T::Currency::resolve(&pot, credit) {
    T::OnUnbalanced::on_unbalanced(credit); // ✅ route it somewhere
}
// or, when burning is intended, say so:
let _ = T::Currency::resolve(&pot, credit).map_err(drop); // ✅ explicit
let _ = T::Currency::resolve(&pot, credit).defensive();   // ✅ logged
```

## Precision and scope

Not reported: `?`, `match`, `if let Err(..)`, `.map_err(..)`, `.inspect_err(..)`, `.unwrap_or_else(..)`, `.defensive()`/`.defensive_proof(..)`, a condition such as `if resolve(..).is_err()`, a binding (even `_`-prefixed) used later, a returned `Result`, and a `Result` whose only imbalance is in `Ok` (e.g. `deposit`). A `.map(..)` chain is reported once, at the call.
