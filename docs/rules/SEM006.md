# SEM006 - DbWeight Estimates Ignore Proof Size

> **Severity:** Warning · **Family:** semantic · **Engine:** compiler-backed (rustc driver) · **Rule name:** `dbweight-missing-pov`

## Description

On a Polkadot parachain, weight is two-dimensional: **ref-time** (execution time on the reference hardware) and **proof size** (the number of bytes the state proof — the PoV, Proof of Validity — contributes when the block is validated on the relay chain). Every block must fit inside hard limits on *both* dimensions, and the relay chain rejects candidate blocks whose PoV is too large.

Hand-written weight expressions built from `T::DbWeight::get().reads(N)`, `.writes(N)`, or `.reads_writes(R, W)` only estimate the ref-time cost of the storage operations. They say nothing about how many bytes those reads pull into the storage proof. A dispatchable that reads a few large storage values can look cheap in ref-time while consuming a huge slice of the PoV budget.

The failure mode is subtle and dangerous: blocks that appear to have plenty of weight left get stuffed with such extrinsics, the accumulated PoV exceeds the limit, and the parachain either produces invalid candidates or stalls block production under load. An attacker who finds an extrinsic whose declared weight underprices its proof-size cost can exploit it to degrade or halt the chain cheaply.

The reliable fix is FRAME benchmarking: benchmarks measure both dimensions and generate `WeightInfo` functions that return a complete two-dimensional `Weight`.

## What it detects

- Any call to `.reads(..)`, `.writes(..)`, or `.reads_writes(..)` where the receiver's resolved type is `RuntimeDbWeight` (i.e. the result of `T::DbWeight::get()`), as confirmed by the compiler's type information.
- Auto-generated weight files (`weights.rs` and files under a `weights/` directory) are excluded, since generated code legitimately uses `DbWeight` as a parameterized fallback.
- The source-analysis fallback additionally skips test and benchmark files.

## What should be avoided

```rust
#[pallet::call_index(0)]
// ❌ only prices ref-time; the bytes read into the PoV are unaccounted for
#[pallet::weight(T::DbWeight::get().reads_writes(2, 1))]
pub fn update_profile(origin: OriginFor<T>, data: ProfileData) -> DispatchResult {
    let who = ensure_signed(origin)?;
    let old = Profiles::<T>::get(&who).ok_or(Error::<T>::NotRegistered)?;
    ensure!(old.locked_until < Now::<T>::get(), Error::<T>::Locked);
    Profiles::<T>::insert(&who, data);
    Ok(())
}
```

The declared weight has a proof-size component of zero, so block building will pack these calls until the actual state proof blows past the PoV limit.

## Best practice

```rust
// ✅ benchmarked weight covering both ref-time and proof size
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::update_profile())]
pub fn update_profile(origin: OriginFor<T>, data: ProfileData) -> DispatchResult {
    let who = ensure_signed(origin)?;
    let old = Profiles::<T>::get(&who).ok_or(Error::<T>::NotRegistered)?;
    ensure!(old.locked_until < Now::<T>::get(), Error::<T>::Locked);
    Profiles::<T>::insert(&who, data);
    Ok(())
}
```

Write a `#[benchmark]` for the extrinsic and let the generated `WeightInfo` implementation supply the full two-dimensional weight, including the `proof_size` term derived from the measured storage footprint.
