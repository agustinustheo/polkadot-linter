# SEC008 - Panics in Production Runtime Code

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `panic-in-production`

## Description

A panic inside runtime code is not a local bug — it is a network event. When a dispatchable or hook panics, the block being built or imported is aborted; if the panicking path is deterministic (for example an `unwrap()` on a storage read that returns `None` for some key), every validator hits the same panic at the same block, and block production stalls. Unlike a returned `DispatchError`, a panic gives FRAME no chance to roll back gracefully, charge the caller, or emit a diagnostic error event.

`unwrap()` and `expect()` are the most common way panics enter pallet code. They are convenient during prototyping, but each call is an implicit assertion that the `Option` is `Some` or the `Result` is `Ok` on every reachable path — including paths an attacker constructs deliberately. If a user-controlled input can steer execution onto the panicking branch, the chain has a remotely triggerable denial-of-service: a single crafted extrinsic can halt the runtime, and in the worst case the chain cannot recover without an emergency intervention.

This rule performs a reachability and flow analysis rather than a plain text match. It only reports `unwrap`/`expect` calls that are reachable from real runtime entry points, and it recognizes the standard ways of proving a value is safe to unwrap (guards, match arms, direct construction), so idiomatic "checked then unwrapped" code is not flagged.

## What it detects

- `.unwrap()` or `.expect(..)` method calls in function bodies reachable from runtime entry points. Entry points are public functions plus FRAME trait implementations: `Hooks::{on_initialize, on_finalize, on_idle, on_poll, on_runtime_upgrade}`, `OnRuntimeUpgrade`/`UncheckedOnRuntimeUpgrade::on_runtime_upgrade`, `ChangeMembers::change_members_sorted`, and XCM `OnResponse::on_response`. Reachability follows the local call graph, so a panic buried in a private helper called from a dispatchable is still reported.
- Calls are **not** reported when the receiver provably cannot panic:
  - the receiver is a `Result` whose error type is uninhabited (`Infallible`, `!`, or an empty enum);
  - the receiver binding was checked on the current path — `if x.is_some()` / `if x.is_ok()` guards, `match` arms matching `Some(..)`/`Ok(..)`, early-return guards such as `if x.is_none() { return ...; }`, or `let`-`else` style exits;
  - the binding was directly assigned `Some(..)` or `Ok(..)` on every path reaching the call (tracked through `if`/`else`, `match` arms, and reassignments).
- One diagnostic is emitted per source line.

## What should be avoided

```rust
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::claim())]
pub fn claim(origin: OriginFor<T>, id: u32) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ❌ panics — and halts the block — for any id with no stored prize
    let prize = Prizes::<T>::get(id).unwrap();

    T::Currency::deposit_creating(&who, prize);
    Ok(())
}
```

Anyone can submit `claim` with an unknown `id`, so the panic is attacker-selectable: one extrinsic aborts block authoring on every node that executes it.

## Best practice

Option 1 — convert the absence into a pallet error:

```rust
pub fn claim(origin: OriginFor<T>, id: u32) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ✅ missing prize becomes a recoverable DispatchError
    let prize = Prizes::<T>::get(id).ok_or(Error::<T>::UnknownPrize)?;

    T::Currency::deposit_creating(&who, prize);
    Ok(())
}
```

Option 2 — for invariants that "should never" fail, use defensive handling instead of a panic:

```rust
use frame_support::defensive;

let Some(prize) = Prizes::<T>::get(id) else {
    // ✅ logs and debug-asserts, but production keeps running
    defensive!("prize must exist for an active claim");
    return Err(Error::<T>::UnknownPrize.into());
};
```

`?`-propagation keeps the failure inside FRAME's transactional dispatch; `defensive!` surfaces broken invariants in tests while keeping mainnet alive.
