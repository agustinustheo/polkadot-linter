# SEC012 - Unbounded clear_prefix limit

| Severity | Default | Engine | Name |
| --- | --- | --- | --- |
| warning | on | compiler (needs the driver) | `unbounded-clear-prefix` |

## What it finds

A `clear_prefix` call on a FRAME storage type has no real deletion limit. The
limit is `None`, `u32::MAX`, `Some(u32::MAX)`, or a local that can hold one of
these values.

## Why it matters

`clear_prefix` deletes one key at a time until it reaches the limit. Without a
limit, it deletes every key under the prefix in one call. Users often control
the number of keys, but the declared weight is fixed. A large prefix can make
the block go over the execution limit or the PoV limit.

## Example

```rust
// Bad: deletes all items in one call.
let _ = Items::<T>::clear_prefix(collection, u32::MAX, None);
Collections::<T>::remove(collection);

// Good: deletes at most 100 items per call.
const CLEAR_BATCH: u32 = 100;
let results = Items::<T>::clear_prefix(collection, CLEAR_BATCH, None);
if results.maybe_cursor.is_none() {
    Collections::<T>::remove(collection);
}
```

## How to fix

1. Give `clear_prefix` a fixed limit.
2. Read `maybe_cursor` from the result.
3. Continue in a later call or block until the cursor is `None`. An `on_idle`
   hook with a `WeightMeter` can do this.

## How it decides

- The limit is the second argument.
- For a local, the rule follows `let`, reassignments, `if`/`else` and `match`.
  If one path can set an unbounded value, the rule reports it.
- It checks code reachable from public functions and FRAME entry points,
  including closure bodies. This includes `#[pallet::call]` dispatchables and
  `try_mutate` closures.

## Configuration

No rule-specific settings. Use `[rules.enabled]` and `[rules.severity]`.
