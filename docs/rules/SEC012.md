# SEC012 - Unbounded clear_prefix Deletion Limit

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `unbounded-clear-prefix`

## Description

`clear_prefix` removes every storage entry under a key prefix, and its `limit` argument is the only thing standing between "delete a batch" and "delete everything in one go". Passing `None` or `u32::MAX` tells the database to keep deleting until the prefix is empty — however many keys that turns out to be. Since the number of keys under a prefix is a property of live chain state (often user-controlled), the real cost of the call is unknowable at development time.

A single-shot unbounded clear is a weight lie: the operation performs one deletion per key while the enclosing extrinsic or hook declares a fixed weight. On a chain where the prefix has grown large, the call blows through the block's execution budget — and on a parachain, the PoV size limit — stalling authoring or producing an invalid block. Users can even weaponize it: inflate the prefix cheaply, then wait for the runtime path that clears it. The deletion also does not pause politely; the overrun happens inside a single state transition that cannot be split retroactively.

The API is designed for incremental use: call `clear_prefix` with a firm limit, inspect the returned cursor (`KillStorageResult` / `MultiRemovalResults`), and continue in a later block or call until the prefix is fully drained. This rule flags call sites that opt out of that protection.

## What it detects

- Calls to `clear_prefix` on compiler-resolved FRAME storage types where the deletion-limit argument (the second argument) is unbounded:
  - a literal `None`,
  - `u32::MAX` (any path ending in `MAX`),
  - `Some(u32::MAX)`, or
  - a local binding that may hold one of those values — the flow analysis tracks such bindings through `let` initializers, reassignments, `if`/`else` branches, and `match` arms, conservatively treating a binding as unbounded if any branch could have made it so.
- Only call sites reachable from runtime entry points (public functions and FRAME trait entry points such as the `Hooks` lifecycle methods and `on_runtime_upgrade`) are analyzed, following the local call graph.

## What should be avoided

```rust
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::retire_collection())]
pub fn retire_collection(origin: OriginFor<T>, collection: CollectionId) -> DispatchResult {
    T::AdminOrigin::ensure_origin(origin)?;

    // ❌ deletes every item under the prefix in one execution path
    let _ = Items::<T>::clear_prefix(collection, u32::MAX, None);

    Collections::<T>::remove(collection);
    Ok(())
}
```

If the collection holds hundreds of thousands of items, this single call performs hundreds of thousands of deletions under a fixed declared weight — enough to exceed the block budget and halt authoring.

## Best practice

Clear in bounded batches and use the returned cursor to continue:

```rust
const CLEAR_BATCH: u32 = 100;

pub fn retire_collection_step(
    origin: OriginFor<T>,
    collection: CollectionId,
) -> DispatchResult {
    T::AdminOrigin::ensure_origin(origin)?;

    // ✅ at most 100 deletions per call; the cursor reports leftovers
    let results = Items::<T>::clear_prefix(collection, CLEAR_BATCH, None);
    if results.maybe_cursor.is_none() {
        // prefix fully drained — finish the retirement
        Collections::<T>::remove(collection);
    }
    Ok(())
}
```

Callers (or an `on_idle` hook with a `WeightMeter`) invoke the step repeatedly until the cursor is exhausted, keeping every block's cost bounded and benchmarkable.
