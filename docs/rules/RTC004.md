# RTC004 - Zero existential or storage deposit

| Severity | Default | Engine | Name |
| --- | --- | --- | --- |
| warning | off | syntax | `zero-deposit-config` |

Off by default: on 10 parachain repositories, 1 of 12 sampled findings was
worth fixing (`benchmarks/precision/2026-11-external`). Most zero deposits were
deliberate or permissioned.

## What it finds

A runtime sets the existential deposit, or a deposit for permissionless
storage, to zero.

## Why it matters

Deposits make callers pay for the state they create. With a zero existential
deposit, accounts are never removed. An attacker can create many accounts for
the cost of transfer fees. With a zero pallet deposit (approvals, asset
accounts, metadata, session keys), any signed account can add storage
permanently for one transaction fee.

## Example

```rust
// Bad
parameter_types! {
    pub const ExistentialDeposit: Balance = 0;
    pub const ApprovalDeposit: Balance = 0;
}
impl pallet_session::Config for Runtime {
    type KeyDeposit = ();
}
```

```rust
// Good
pub const EXISTENTIAL_DEPOSIT: Balance = MILLICENTS;
parameter_types! {
    pub const ExistentialDeposit: Balance = EXISTENTIAL_DEPOSIT;
    pub const ApprovalDeposit: Balance = EXISTENTIAL_DEPOSIT;
}
```

## How to fix

Set each deposit from the storage cost of the item it pays for.

## How it decides

- It reports a deposit-named constant (`const`, `parameter_types!`, or
  `Const*<0>`) whose value is zero. `0`, `0u128`, `0 as Balance` and
  `0 * UNIT` are all zero. Names that start with `Max` or `Min` are not
  deposits.
- It reports `type XDeposit = ();` for amount-shaped names (`*Deposit`,
  `*DepositBase`, `*DepositPer*`, `*DepositFactor`). `()` returns
  `Default::default()`, which is zero.
- It skips a deposit when only a privileged origin can do the action:
  `*SubmissionDeposit` with a privileged `SubmitOrigin`, and `*AssetDeposit` or
  `MetadataDeposit*` with a privileged `CreateOrigin`.
- An origin is privileged only when every caller it admits is privileged.
  `EnsureRoot`, `EnsureSignedBy`, `EnsureMember`, `EnsureOfRank` and similar
  are privileged. `EitherOf<L, R>` is privileged only when both sides are.
  `EnsureSigned`, and origins defined in other files, are not.
- `ApprovalDeposit`, `AssetAccountDeposit` and the existential deposit are
  never skipped. Any signed account can do those actions.

## Limits

- It skips bare `Deposit` (pallet-revive) and `InvulnerableDeposit`.
- It skips `type KeyDeposit = ();` when the file filters
  `Session(.. set_keys ..) => false`, as the relay chains do.
- It skips items behind `runtime-benchmarks` or `try-runtime`.
- It does not resolve origins in other files. A constant used only from another
  file is reported.
- Pinned SDK: 14 findings on Westend, Rococo and system chains, all correct.
  Most are `type KeyDeposit = ();`, which fellows runtimes fixed in
  [#1310](https://github.com/polkadot-fellows/runtimes/pull/1310).

Runtime scope: see [Runtime configuration rules](runtime-config.md).

## Configuration

No rule-specific settings. Enable it with `RTC004 = true` under
`[rules.enabled]`.
