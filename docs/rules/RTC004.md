# RTC004 - Zero Existential or Storage Deposit

> **Severity:** Warning · **Family:** runtime-config · **Engine:** source analysis (syn) · **Rule name:** `zero-deposit-config`

## Description

Deposits make permissionless callers pay for the state they create. The existential deposit is the deposit for an account itself: with it set to zero, accounts are never reaped, and an attacker can create unlimited accounts for the price of transfer fees. Pallet-level deposits (`ApprovalDeposit`, `AssetAccountDeposit`, `MetadataDepositPerByte`, `DepositPerByte`, ...) cover approvals, asset accounts, metadata, and contract storage. A zero value lets any signed account write that storage for a transaction fee alone, and the bloat is permanent.

## What it detects

In non-test runtime code:

- an `ExistentialDeposit` / `EXISTENTIAL_DEPOSIT` constant equal to zero, or an associated type `type ExistentialDeposit = ConstU128<0>;` (any `Const*<0>`);
- any other deposit-named constant (name contains `Deposit`, excluding `Max*`/`Min*` counts) equal to zero, in a `const` item, a `parameter_types!` entry, or a `Config` associated type set to `Const*<0>`.

Constants are `const` items and every `parameter_types!` form: `pub const X: T = v;`, the const-less `pub X: T = v;` and `pub storage X: T = v;` (see `frame/support/src/macros.rs`). A value is zero when it is a zero literal, possibly cast, parenthesised, in a block, or scaled: `0`, `0u128`, `0 as Balance`, `0 * UNIT`, `UNIT * 0`, `0 * DOLLARS / 100`, `ConstU128<{ 0 * CENTS }>`.

### Origin-gated exemption

A zero deposit is not a spam vector when only a privileged origin can perform the action it guards. The rule skips:

- `*SubmissionDeposit` when the consuming `Config` impl's `SubmitOrigin` is privileged;
- `*AssetDeposit`, `MetadataDepositBase` and `MetadataDepositPerByte` when the impl's `CreateOrigin` is privileged.

An origin counts as privileged only when the rule can prove that every caller it admits is privileged:

- `EnsureRoot`, `EnsureRootWithSuccess`, `EnsureSignedBy`, `EnsureMember`, `EnsureMembers`, `EnsureOfRank`, `EnsureRankedMember`, `EnsureProportionAtLeast`, `EnsureProportionMoreThan` and `EnsureNever` are privileged;
- `EitherOf<L, R>` and `EitherOfDiverse<L, R>` are privileged only if **both** branches are;
- `AsEnsureOriginWithArg<O>`, `EnsureWithSuccess<O, ..>`, `MapSuccess<O, ..>` and `TryMapSuccess<O, ..>` are privileged if `O` is, and `TryWithMorphedArg<_, _, _, Inner, _>` if `Inner` is;
- a bare name is resolved through `type` aliases in the same file;
- anything else, including `EnsureSigned`, `ForeignCreators`, and origins defined in other files, is treated as permissionless, so it does not exempt the deposit.

`EitherOfDiverse<EnsureRoot<AccountId>, PublicSubmissionOrigin>` is therefore not exempt, because one branch is open (or unknown). The diagnostic says that cross-file origin gates are not resolved. For a `parameter_types!` constant, every impl in the same file that binds it must be gated; a constant consumed only from another file is reported, because the rule cannot see its consumer's origin. `ApprovalDeposit`, `AssetAccountDeposit` and the existential deposit are never exempt, because `approve_transfer`, `touch` and account creation are open to any signed account.

Items gated on `runtime-benchmarks` or `try-runtime` are ignored.

## Runtime scope

Same as all RTC rules; see [Runtime Configuration Rules](runtime-config.md). penpal (dev) zeroes its asset and contract deposits on purpose and is reported only with `include_dev_runtimes = true`.

## What should be avoided

```rust
parameter_types! {
    pub const ExistentialDeposit: Balance = 0;   // ❌ accounts never reaped
    pub const ApprovalDeposit: Balance = 0;      // ❌ free approvals
}
```

## Best practice

```rust
pub const EXISTENTIAL_DEPOSIT: Balance = MILLICENTS; // > 0, derived from per-account storage cost

parameter_types! {
    pub const ExistentialDeposit: Balance = EXISTENTIAL_DEPOSIT;
    pub const ApprovalDeposit: Balance = EXISTENTIAL_DEPOSIT;
}
```
