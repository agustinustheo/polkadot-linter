# SEC014 - Identity Hasher on Common Key Types

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `identity-hasher-on-common-keys`

## Description

Every FRAME storage map chooses a hasher that turns the map key into part of the trie key. `Blake2_128Concat` (cryptographic) and `Twox64Concat` (fast, non-cryptographic) both prepend a hash before the encoded key; `Identity` skips hashing entirely and places the raw encoded key directly into the trie.

`Identity` is a legitimate optimisation when the keys are already uniformly distributed and outside user control — for example, keys that are themselves cryptographic hashes. But when the key is a plain scalar such as a `u32`, `u64`, block number, or balance, the trie keys become fully predictable and, in many pallets, attacker-choosable. That allows an adversary to pick key values that cluster in one region of the trie, producing deep, unbalanced branches. Lookups and proofs for those branches become disproportionately expensive, inflating PoV size and making storage operations cost more than their benchmarked weight assumed.

Sequential scalar keys also tend to concentrate writes in adjacent trie nodes, so even without an attacker the trie can degrade compared to a hashed layout. Unless the map's design specifically depends on the raw-key ordering (ring buffers, index segments), a hashing hasher is the safe default.

## What it detects

- A `#[pallet::storage]` map (`StorageMap`, `CountedStorageMap`, or either key of a `StorageDoubleMap`) that pairs the `Identity` hasher with a common key type.
- "Common key types" are resolved by the compiler as: `u32`, `u64`, or an associated type whose path ends in `::Balance` or `::BlockNumber`.
- Hasher and key types are matched after resolving type aliases, so `Identity` hidden behind a project-local alias is still found.
- Suppressed for `u32`/`u64` keys when the storage item's doc comments describe an intentional numeric layout (markers such as "ring buffer", "index", "indices", "segment", or "position"), since those designs rely on raw-key adjacency.

## What should be avoided

```rust
#[pallet::storage]
pub type Bids<T: Config> = StorageMap<
    _,
    Identity,               // ❌ raw key becomes the trie key
    u64,                    // attacker-choosable auction id
    Bid<T::AccountId>,
>;
```

Because auction ids are chosen by callers, an attacker can craft ids whose byte patterns cluster in the trie, degrading proof sizes and lookup costs for everyone.

## Best practice

Option 1 — hash untrusted or predictable keys:

```rust
#[pallet::storage]
pub type Bids<T: Config> = StorageMap<
    _,
    Blake2_128Concat,       // ✅ cryptographic dispersion
    u64,
    Bid<T::AccountId>,
>;
```

`Blake2_128Concat` guarantees uniform key dispersion regardless of who chooses the key; use `Twox64Concat` only when keys cannot be influenced by untrusted callers.

Option 2 — if the raw layout is genuinely required, document it:

```rust
#[pallet::storage]
/// Ring buffer of recent headers; the index layout is relied upon for
/// sequential iteration.
pub type RecentHeaders<T: Config> = StorageMap<_, Identity, u32, T::Hash>;
```

A doc comment explaining the numeric-layout dependency both suppresses the warning and tells reviewers why `Identity` is intentional.
