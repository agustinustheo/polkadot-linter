# SEM012 - Suppressed Dead Code in Production Pallet Code

> **Severity:** Warning · **Family:** semantic · **Engine:** source analysis (syn) · **Rule name:** `allow-dead-code-in-pallet`

## Description

Runtime pallets are long-lived, security-sensitive codebases that get audited, forked, and upgraded many times over their lifetime. Every line of code in a pallet is a line an auditor must read and a maintainer must reason about. Dead code — functions, types, constants, or fields that nothing calls — adds review surface without adding behavior, and it tends to rot: it stops compiling against new SDK versions, encodes stale assumptions about storage layout, and confuses developers into believing a code path is still live.

`#[allow(dead_code)]` (or the crate-level `#![allow(dead_code)]`) does not fix any of this; it merely silences the compiler's warning that something is unused. In production pallet code that suppression usually means one of two things: genuinely dead code that should be deleted, or code that *should* be wired up but was accidentally disconnected — for example a validation helper that is no longer called from any dispatchable. The second case is the dangerous one: the allow attribute hides exactly the signal that would have revealed the missing call.

The right response to a `dead_code` warning in a pallet is almost always to remove the code (version control preserves history if it is ever needed again), or to actually use it. Suppressing the warning should be reserved for generated code, which this rule already exempts.

## What it detects

- Any `#[allow(...)]`-style attribute whose argument list contains `dead_code`, attached to an item (`fn`, `struct`, `enum`, `impl`, `mod`, `const`, `static`, `trait`, `type`, `use`, etc.) or applied at file level (`#![allow(dead_code)]`).
- Only in production code: test files and `#[cfg(test)]` modules are skipped.
- Auto-generated weight files are exempt: paths under a `weights/` directory or ending in `weights.rs` are ignored, since generated `WeightInfo` implementations legitimately carry `#![allow(dead_code)]`.

## What should be avoided

```rust
#[allow(dead_code)]
fn ensure_not_frozen(account: &T::AccountId) -> DispatchResult {
    ensure!(!Frozen::<T>::contains_key(account), Error::<T>::AccountFrozen);
    Ok(())
}

#[pallet::call]
impl<T: Config> Pallet<T> {
    #[pallet::call_index(0)]
    #[pallet::weight(T::WeightInfo::transfer())]
    pub fn transfer(origin: OriginFor<T>, dest: T::AccountId, amount: BalanceOf<T>) -> DispatchResult {
        let who = ensure_signed(origin)?;
        // ensure_not_frozen is never called — the freeze check silently vanished
        Self::do_transfer(&who, &dest, amount)
    }
}
```

The `allow` attribute hides the compiler's warning that `ensure_not_frozen` is unused — which in this case is a missing security check, not harmless clutter.

## Best practice

Option 1 — use the code if it was meant to be live:

```rust
pub fn transfer(origin: OriginFor<T>, dest: T::AccountId, amount: BalanceOf<T>) -> DispatchResult {
    let who = ensure_signed(origin)?;
    Self::ensure_not_frozen(&who)?; // ✅ warning disappears because the helper is used
    Self::do_transfer(&who, &dest, amount)
}
```

Option 2 — delete code that is genuinely dead:

```rust
// ✅ The helper is removed entirely; git history keeps it retrievable.
// No #[allow(dead_code)] anywhere in the pallet.
```

Either way, the compiler's `dead_code` lint stays active and keeps guarding against future accidental disconnections.

## Configuration

```toml
[rules.severity]
"SEM012" = "warning"

[rules.enabled]
"SEM012" = false
```

There are no rule-specific configuration keys. Generated weight files (`weights/` directories and `*weights.rs`) are always exempt.
