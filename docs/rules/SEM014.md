# SEM014 - Missing Log Target in SubmitTransaction Logging

> **Severity:** Advisory · **Family:** semantic · **Engine:** source analysis (syn) · **Rule name:** `submit-transaction-log-target`

## Description

Offchain workers submit transactions back into the pool with `SubmitTransaction::<T, Call<T>>::submit_transaction(...)` (or the unsigned variant). This path fails in ways that are invisible on-chain: the pool can reject the transaction as stale or duplicate, the call may fail validation, or the node may simply not be an authority. The only evidence is the node's log output — there is no event, no storage change, and no extrinsic to inspect.

A node's log stream is shared by the client, consensus, networking, and every pallet in the runtime. Rust's `log` macros support a `target:` argument precisely so that operators can filter this firehose: with a stable per-pallet target such as `target: LOG_TARGET` (conventionally `const LOG_TARGET: &str = "runtime::my-pallet";`), an operator can run the node with `-l runtime::my-pallet=trace` and see exactly the submission attempts and their outcomes. Without a target, the message is attributed to the enclosing module path, which is unstable across refactors and unknown to whoever is debugging the deployment.

Descriptive, filterable logging around transaction submission is cheap to add and pays for itself the first time an offchain worker silently stops submitting on a production network.

## What it detects

- A line that performs an offchain submission — it contains both `SubmitTransaction::<` and `submit_transaction` — followed within the next 12 lines by a `log::trace!`, `log::debug!`, `log::info!`, `log::warn!`, or `log::error!` invocation.
- If that log invocation (inspected across a few following lines, since log calls often span multiple lines) does not contain a `target:` argument, the rule flags the log call.
- Test files and `#[cfg(test)]` modules are skipped.

## What should be avoided

```rust
// ❌ submission outcome logged without a target
match SubmitTransaction::<T, Call<T>>::submit_transaction(xt) {
    Ok(()) => log::debug!("submitted price update for round {round}"),
    Err(e) => log::error!("failed to submit price update: {e:?}"),
}
```

These messages land in the global log stream under an incidental module path, so an operator cannot enable or filter them per pallet when diagnosing why the offchain worker's transactions never appear on chain.

## Best practice

```rust
const LOG_TARGET: &str = "runtime::price-oracle";

// ✅ every submission log routes through the pallet's stable target
match SubmitTransaction::<T, Call<T>>::submit_transaction(xt) {
    Ok(()) => log::debug!(target: LOG_TARGET, "submitted price update for round {round}"),
    Err(e) => log::error!(
        target: LOG_TARGET,
        "failed to submit price update for round {round}: {e:?}"
    ),
}
```

Now `-l runtime::price-oracle=trace` surfaces exactly the submission path, and the target stays stable even if the module is moved.
