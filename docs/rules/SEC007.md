# SEC007 - Discarded Result via Let-Underscore

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `let-underscore-result`

## Description

Binding a `Result` to `_` silently throws away the error path. In ordinary application code this is sloppy; in a FRAME pallet it can corrupt on-chain state. Many Substrate APIs — balance transfers, reserves, XCM sends, `try_mutate`, `try_push` on bounded collections — report failure through their `Result`, and the surrounding logic usually assumes the operation succeeded. When the returned error is discarded with `let _ =`, the extrinsic continues down its happy path and commits every later storage write, even though an earlier step failed.

The pattern is especially dangerous because it often starts as a typo: a developer intends to propagate the error with `?` but writes `let _ = ...` (or drops the `?` during a refactor), and the compiler stops warning about the unused `Result`. From that point on, a failed reserve or a failed transfer no longer aborts the call. An attacker who can reliably trigger the failing branch — for example by draining an account below the required reserve — gets the rest of the dispatchable executed for free, with no rollback, no error event, and no trace in block explorers.

Unlike a dispatchable that returns `Err` (where FRAME rolls back the whole transaction), a swallowed error leaves partial state in place permanently. If the error genuinely cannot happen or genuinely does not matter, that decision should be visible in the code — via `.expect(...)` with a proof, a `defensive!`-style handler, or at minimum explicit handling of the `Err` arm — not hidden behind a wildcard binding.

## What it detects

- A `let _ = <expr>;` statement (wildcard pattern, no bindings) where the initializer's compiler-resolved type is `Result<T, E>`.
- The error type `E` must be meaningful: results whose error type is the unit type `()` are not reported, since there is nothing to inspect or propagate.
- The check runs on every function body in the compiled crate and reports at most one diagnostic per source line.

Because the rule is compiler-backed, the `Result` type is resolved through rustc's type checker: type aliases, generic returns such as `DispatchResult`, and macro-expanded code are all seen with their real types rather than matched by name.

## What should be avoided

```rust
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::enroll())]
pub fn enroll(origin: OriginFor<T>) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ❌ if the reserve fails, enrollment proceeds anyway
    let _ = T::Currency::reserve(&who, T::EnrollmentDeposit::get());

    Members::<T>::insert(&who, MemberInfo::default());
    Ok(())
}
```

If `reserve` fails (insufficient free balance), the account is still inserted into `Members` — the pallet now tracks a member who never paid the deposit, and the discrepancy is invisible on-chain.

## Best practice

Option 1 — propagate the error so FRAME rolls back the extrinsic:

```rust
pub fn enroll(origin: OriginFor<T>) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ✅ a failed reserve aborts the call and reverts all state changes
    T::Currency::reserve(&who, T::EnrollmentDeposit::get())?;

    Members::<T>::insert(&who, MemberInfo::default());
    Ok(())
}
```

Option 2 — when discarding really is intended, handle the error explicitly so the decision is auditable:

```rust
// ✅ best-effort notification: failure is logged, not silently dropped
if let Err(e) = T::Notifier::notify(&who) {
    log::warn!(target: "runtime::membership", "notify failed: {e:?}");
}
```

Propagation with `?` is the right default inside dispatchables; explicit `if let Err(..)` handling documents the rare cases where continuing is correct.
