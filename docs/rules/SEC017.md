# SEC017 - Unbounded Vec Fields in Pallet Events

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `vec-in-events`

## Description

Events are not free. Every deposited event is SCALE-encoded into the `System::Events` storage item for the duration of the block, hashed into the events root, stored by archive nodes, and decoded by every indexer and front-end that follows the chain. The weight model assumes event payloads are small and roughly constant-size.

A `Vec<T>` field in an event breaks that assumption: the payload is as large as whatever the runtime happens to put in it. When the vector originates from extrinsic input, a caller can pay the fixed base fee while forcing the chain to encode, hash, and persist kilobytes of event data — a classic asymmetric-cost vector. Even without malice, echoing large inputs back through events inflates block size and PoV for no benefit, since the caller already knows the data they submitted.

The fix is almost always to shrink the payload: emit a bound (`BoundedVec`), a hash or count of the data, or several small events — clients that need the full data can read it from storage or from the extrinsic itself.

## What it detects

- Fields of `#[pallet::event]` enum variants whose resolved type contains an unbounded `Vec` (including `Vec` nested inside generics, tuples, or arrays, and behind type aliases). `BoundedVec` and `WeakBoundedVec` fields are exempt.
- A candidate field is reported when the event enum is a real FRAME event (its marker attributes, such as `#[pallet::generate_deposit]`, are consumed by the pallet macro), or when dataflow analysis shows an unbounded value flowing into that field at a `deposit_event` call site.
- Dataflow suppression: if the vector deposited into the event is a dispatchable parameter whose length is already accounted for in the `#[pallet::weight(...)]` expression, the caller pays proportionally and the field is not flagged.

## What should be avoided

```rust
#[pallet::event]
#[pallet::generate_deposit(pub(super) fn deposit_event)]
pub enum Event<T: Config> {
    /// A batch of remarks was recorded.
    RemarksStored {
        who: T::AccountId,
        remarks: Vec<Vec<u8>>, // ❌ caller-sized payload copied into events
    },
}
```

The entire user-supplied payload is re-encoded into block event storage, so callers can inflate every block's event data at fixed cost.

## Best practice

Option 1 — emit a fixed-size summary instead of the data:

```rust
#[pallet::event]
#[pallet::generate_deposit(pub(super) fn deposit_event)]
pub enum Event<T: Config> {
    /// A batch of remarks was recorded.
    RemarksStored {
        who: T::AccountId,
        count: u32,          // ✅ constant-size
        batch_hash: T::Hash, // ✅ commitment to the data, if clients need one
    },
}
```

Indexers can correlate the hash with the extrinsic body; the chain never duplicates the payload.

Option 2 — if the payload itself must be in the event, bound it:

```rust
pub enum Event<T: Config> {
    NoteRecorded {
        who: T::AccountId,
        note: BoundedVec<u8, T::MaxNoteLength>, // ✅ statically bounded
    },
}
```

A `BoundedVec` caps the worst-case event size at a value the runtime chose, keeping event weight assumptions honest.
