# RTC009 - Known-Vulnerable Polkadot Crate Version in Cargo.lock

> **Severity:** Error · **Family:** runtime-config · **Engine:** lockfile analysis · **Rule name:** `known-vulnerable-crate-version`

## Description

Some Polkadot security fixes ship as patch releases on each supported release line without a RustSec or GHSA advisory, so `cargo audit` and `cargo deny` may not report them (no RustSec advisory existed when the row was added). A runtime keeps the bug until its `Cargo.lock` picks up the patch release and a runtime upgrade ships.

The Oct 2026 dotUSD exploit (~$1.38M) is the motivating case. The `staging-xcm-executor` `WithdrawAsset` regression ([#10384](https://github.com/paritytech/polkadot-sdk/pull/10384)) was fixed on master in June 2026 ([#11910](https://github.com/paritytech/polkadot-sdk/pull/11910)). Production runtimes kept `staging-xcm-executor 28.0.1` until the stable2606 backport ([#13531](https://github.com/paritytech/polkadot-sdk/pull/13531), `28.1.0`) reached fellows runtime 2.5.1 ([runtimes#1331](https://github.com/polkadot-fellows/runtimes/pull/1331)) in late October.

## What it detects

A `[[package]]` in a `Cargo.lock` that comes from crates.io (`registry+https://github.com/rust-lang/crates.io-index` or `sparse+https://index.crates.io/`) and whose version falls in a vulnerable range from [`src/rules/vulnerable_crates.tsv`](../../src/rules/vulnerable_crates.tsv). Each row covers one major (release) line: from the first vulnerable version up to, but not including, the first fixed version on that line. The diagnostic names the advisory, its URL, the installed version and the minimum fixed version on that line. If the line never got a fix, it names the nearest fixed release on a later line.

| Crate | Affected | First fixed | Advisory |
| --- | --- | --- | --- |
| `staging-xcm-executor` | 18.0.1-18.0.5, 21.0.0 | none on those lines | [InitiateTransfer origin leak](https://forum.polkadot.network/t/postmortem-xcm-initiatetransfer-origin-leak/17357) (Feb 2026) |
| `staging-xcm-executor` | 19.1.0-19.1.3, 20.0.0-20.0.1, 22.0.0, 23.0.0, 24.0.0 | 19.1.4, 20.0.2, 22.0.1, 23.0.1, 24.0.1 | same |
| `staging-xcm-executor` | 25.0.0-25.1.0, 26.0.0, 27.0.0, 28.0.0-28.0.1 | 25.2.0 ([#12476](https://github.com/paritytech/polkadot-sdk/pull/12476)), none, 27.1.0 ([#13535](https://github.com/paritytech/polkadot-sdk/pull/13535)), 28.1.0 ([#13531](https://github.com/paritytech/polkadot-sdk/pull/13531)) | dotUSD: `WithdrawAsset` imbalance escapes the transactional rollback |

Every boundary was checked against the published crate source on crates.io, not only the changelogs. The vulnerable `if preserve_origin { if let Some(..) = origin.filter(..) { AliasOrigin } } else { ClearOrigin }` shape first appears in 18.0.1 (18.0.0 and the yanked 19.0.0 return `BadOrigin` instead). The `let mut withdrawn` declared outside `TransactionalProcessor::process` exists only in the listed 25.x-28.x versions. 29.0.0 shipped with both fixes.

Path, git and private-registry packages are skipped. Path and git packages are the workspace's own code (polkadot-sdk itself) or an unreleased revision, and a private registry can serve a patched fork under the same name and version, so the version number says nothing about them. Pre-release versions are skipped too.

## Scope

Every `Cargo.lock` the scan reaches is checked, not only runtime crates. A vulnerable executor in any lockfile means some crate in that workspace builds it. Excluding `*.lock` in `[general] exclude` turns the rule off.

## Scope of the advisory list

The list holds only Polkadot-specific fixes that have no RustSec/GHSA entry. Generic crates are left to `cargo audit` / `cargo deny`, so the two tools don't report the same advisories. Add a row only after checking the boundary in the published crate source, and cite the fix or postmortem URL.

## Scope and maintenance

The table is current as of 2026-11. The polkadot-linter maintainers update it. Each polkadot-sdk security postmortem, and each stable patch release that carries a security fix, triggers a review: add a row for every affected release line, checked against the published crate source.

The list is incomplete. It covers only the advisories above. Git-sourced dependencies (for example the moonbeam, hydration or peaq polkadot-sdk forks) are not checked. A silent RTC009 does not mean the lockfile is safe.

## What should be avoided

```toml
[[package]]
name = "staging-xcm-executor"
version = "28.0.1" # dotUSD WithdrawAsset bug; stable2606 fix is 28.1.0
source = "registry+https://github.com/rust-lang/crates.io-index"
```

## Best practice

Bump to the first fixed release on your line (`cargo update -p staging-xcm-executor --precise 28.1.0`, or psvm for a full SDK patch release), rebuild the runtime and ship it in a runtime upgrade.

## Configuration

```toml
[rules.enabled]
"RTC009" = false
```

## Oracle

polkadot-fellows/runtimes `Cargo.lock`:

| Revision | `staging-xcm-executor` | RTC009 |
| --- | --- | --- |
| `66945c6265` (parent of the 2.5.1 release, #1331) | 28.0.1 | fires (dotUSD, fix 28.1.0) |
| `ebfa4d7b98` (Release 2.5.1, #1331) and main (`711471a244`, 2026-11-05) | 28.1.0 | silent |
| `4e17c8e79` (2026-01-16) | 23.0.0 | fires (InitiateTransfer, fix 23.0.1) |
| `985df2582` (2026-02-20, Release 2.1.0 prep) | 24.0.1 | silent |

polkadot-sdk master builds the executor from its own path package, so it has no findings.
