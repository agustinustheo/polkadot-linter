# RTC009 - Known-vulnerable Polkadot crate version

| Severity | Default | Engine | Name |
| --- | --- | --- | --- |
| error | on | syntax (reads `Cargo.lock`) | `known-vulnerable-crate-version` |

## What it finds

A `Cargo.lock` pins a Polkadot crate version that has a known security bug. The
fix shipped as a quiet patch release, with no RustSec or GHSA advisory.

## Why it matters

`cargo audit` and `cargo deny` do not report these bugs. A runtime keeps the
bug until its `Cargo.lock` gets the patch release and a runtime upgrade ships.

The October 2026 dotUSD exploit (about $1.38M) used such a bug. Master fixed it
in June 2026 ([#11910](https://github.com/paritytech/polkadot-sdk/pull/11910)).
Production runtimes kept `staging-xcm-executor 28.0.1` until fellows runtime
2.5.1 ([runtimes#1331](https://github.com/polkadot-fellows/runtimes/pull/1331))
in late October.

## Example

```toml
# Bad: dotUSD WithdrawAsset bug. The fix on this line is 28.1.0.
[[package]]
name = "staging-xcm-executor"
version = "28.0.1"
source = "registry+https://github.com/rust-lang/crates.io-index"
```

## How to fix

1. Update to the first fixed version on your release line, for example
   `cargo update -p staging-xcm-executor --precise 28.1.0`. You can also use
   psvm for a full SDK patch release.
2. Build the runtime again.
3. Ship it in a runtime upgrade.

## Affected versions

The list is in
[`src/rules/vulnerable_crates.tsv`](https://github.com/agustinustheo/polkadot-linter/blob/main/src/rules/vulnerable_crates.tsv).
Each row covers one release line. A version is affected from the first
vulnerable version up to the first fixed version on that line.

| Crate | Affected | First fixed | Advisory |
| --- | --- | --- | --- |
| `staging-xcm-executor` | 18.0.1-18.0.5, 21.0.0 | no fix on these lines | [InitiateTransfer origin leak](https://forum.polkadot.network/t/postmortem-xcm-initiatetransfer-origin-leak/17357) (Feb 2026) |
| `staging-xcm-executor` | 19.1.0-19.1.3, 20.0.0-20.0.1, 22.0.0, 23.0.0, 24.0.0 | 19.1.4, 20.0.2, 22.0.1, 23.0.1, 24.0.1 | same |
| `staging-xcm-executor` | 25.0.0-25.1.0, 26.0.0, 27.0.0, 28.0.0-28.0.1 | 25.2.0, no fix for 26, 27.1.0, 28.1.0 | dotUSD: `WithdrawAsset` imbalance escapes the rollback ([SEC019](SEC019.md)) |

29.0.0 has both fixes. Each boundary was checked in the published crate source.
If a line has no fix, the message names the nearest fixed release on a later
line.

## Limits

- It checks only crates.io packages. It skips path, git and private-registry
  packages, because their version number does not show the code. Forks such as
  the moonbeam or hydration SDK forks are not checked.
- It skips pre-release versions.
- When `Cargo.lock` sits in a Cargo workspace with at least one included
  production runtime (local or external) rooted in the lockfile, RTC009 walks
  `Cargo.lock` dependency edges and downgrades entries unreachable from any
  included production runtime to `advisory` severity and `low` confidence
  (instead of dropping them). Note that `Cargo.lock` merges dev- and
  build-dependencies of a runtime crate, so those remain reachable. For
  standalone lockfiles or workspaces with no included runtime rooted in
  `Cargo.lock`, every crates.io package is reported at `error` severity.
- A local runtime is the `Cargo.lock` package with its name and version and
  no `source`. The version is the manifest string, the `[workspace.package]`
  version for `version.workspace = true`, or `0.0.0` when the manifest has
  none. If the inherited version is not stated, the runtime matches only when
  exactly one `source`-less package has its name. Runtimes of another
  workspace (a nearer `[workspace]`) are ignored, because they have their own
  lockfile. The search for the workspace stops at a directory with a
  `Cargo.lock`, so a standalone runtime that a parent workspace excludes
  matches its own lockfile.
- If an included local runtime matches no package (a stale lockfile, or an
  unknown version with several candidates), the lockfile does not show what it
  reaches, so RTC009 does not downgrade anything in that lockfile.
- Every other package is an external root when it passes the test, dev and
  testnet name filters and one of these is true:
  - It depends on `substrate-wasm-builder`, directly or through other
    packages (the `polkadot-sdk` umbrella, a helper build crate). The search
    passes through a package that the name filters exclude.
  - Its name ends in a `runtime` token.
  - It depends directly on `frame-executive`, as every FRAME runtime does.
  - It has a `runtime` token elsewhere in its name (`runtime-eden`,
    `interlay-runtime-parachain`).
  - It has no `source` and no crate of this workspace has its name and
    version (a member in a hidden directory, a path package outside the
    workspace or in another workspace), so the parser did not read it.

  Names that start with `sp-`, `bp-` or `frame-try-` (`sp-runtime`,
  `sp-runtime-interface`, `bp-runtime`, `frame-try-runtime`) do not count as
  runtime names. These signals cover git and registry runtimes, path runtimes
  outside the workspace, symlinked or hidden members and runtimes the parser
  does not recognise. The `frame-executive` edge and an inner `runtime` token do not
  make a root of a `source`-less entry of a local package that the parser read
  and found is not a runtime, such as a pallet with `frame-executive` as a
  dev-dependency. RTC009 does not parse a package whose Rust files outside
  test paths have no `construct_runtime` and no `runtime` before `]` or `(`.
  Such a package is not a proven library, so both signals still apply to it.
  A package that only a local runtime excluded by the filters matches is not
  a root. Libraries such as `polkadot-runtime-common` are roots by name, which
  keeps their dependencies at `error`.
- `Cargo.lock` resolves every feature of a workspace member, so it keeps a
  member's optional `substrate-wasm-builder` build dependency. For a package
  outside the workspace it keeps an optional dependency only when some feature
  enables it. A git or registry runtime that its node takes with
  `default-features = false` can therefore lack the builder edge, which is why
  a package named like a runtime is a root without one. Checked with
  `cargo generate-lockfile` (Cargo 1.93).
- Git dependency entries in `Cargo.lock` omit the `#<commit>` that the
  package's `source` has, so sources are compared without it. When the
  source of an entry matches no package, the edge goes to every package with
  that name and version.
- For advisories with `precondition = asset_transactor` (the `WithdrawAsset`
  rollback lines `25.x–28.x`), the finding is downgraded to `advisory`
  severity and `low` confidence when every reaching production runtime is a
  local runtime where all of these are true, because withdrawal debits are not
  reachable:
  - An impl's trait path resolves to `xcm_executor::Config` or
    `staging_xcm_executor::Config`, through the module's `use` items and
    renames. A self type named `XcmConfig` is not enough.
  - Every impl in the crate with a `type AssetTransactor` sets it to `()`, and
    every executor impl has one.
  - `pallet_xcm::Config` sets `type XcmExecutor = XcmExecutor<X>`, and `X` and
    every other `XcmExecutor<..>` in the crate, in types, expressions and
    under a `use` rename, name exactly one visible executor impl. A path
    matches an impl by its full path from the crate root, through the
    module's `use` items, so `other::XcmConfig` or an extern crate path does
    not match a local `XcmConfig`. An executor from `include!` or a macro is
    not visible, and a path inside a function body does not resolve, so
    either keeps the finding.

  An alias counts as `()` only when its `type` item is the only item in the
  impl's module that defines the name and has no `#[cfg]` or `#[cfg_attr]`. A
  `use`, `struct`, `enum`, gated item or glob import in that module, or a
  generic parameter of the impl, makes the alias unknown, which is not `()`.
  `r#Name` and `Name` are the same name. An external root is never mitigated,
  and neither is a package that two parsed crates match.
- RTC009 reads the workspace's crates only for a lockfile with an affected
  package.
- The list is incomplete and current as of 2026-11. If RTC009 reports nothing,
  the lockfile can still be unsafe. Use `cargo audit` or `cargo deny` for
  generic crates.
- Allow comments do not work in `Cargo.lock`. Use a baseline to hide a finding.
- Evidence: polkadot-fellows/runtimes `66945c6265` (28.0.1) and `4e17c8e79`
  (23.0.0) fire. The fixed releases do not fire.

## Configuration

No rule-specific settings. Use `[rules.enabled]` and `[rules.severity]`.

## Adding a row

Add a row only for a Polkadot-specific fix with no RustSec or GHSA entry. Check
the boundary in the published crate source. Cite the fix or the postmortem URL.
