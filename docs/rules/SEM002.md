# SEM002 - Prefer Turbofish Syntax for collect()

> **Severity:** Advisory · **Family:** semantic · **Engine:** source analysis (syn) · **Rule name:** `prefer-collect-turbofish`

## Description

`Iterator::collect` needs a target type, and Rust accepts it in two places: an
explicit type annotation on the `let` binding
(`let xs: Vec<u32> = iter.collect();`) or a turbofish on the call itself
(`let xs = iter.collect::<Vec<u32>>();`). Both compile to identical code; this
rule enforces the project convention of using the turbofish form.

The rationale is readability in the kind of long adapter chains that pallet
code accumulates. With the turbofish, the type sits directly on the operation
that needs it — the reader reaches the end of a `filter`/`map` chain and
immediately sees what it collects into. With a binding annotation, the type is
separated from the `collect()` call by the whole chain, and in multi-line
expressions the two can be a dozen lines apart. Keeping the type at the call
site also survives refactors better: if the binding is inlined or the chain is
moved into an expression position, the turbofish travels with it.

This is a pure style convention with Advisory severity — there is no runtime
or security impact, only consistency across the codebase.

## What it detects

- A `let` binding with an explicit type annotation containing `Vec` whose
  initializer is a direct `.collect()` method call without a turbofish, e.g.
  `let ids: Vec<T::AccountId> = source.iter().map(...).collect();`.
- Bindings collecting into non-`Vec` types, and `collect()` calls that already
  carry a turbofish, do not trigger the rule.

## What should be avoided

```rust
fn active_voters(proposal: &Proposal<T>) -> Vec<T::AccountId> {
    // ❌ The target type is annotated on the binding, far from `.collect()`.
    let voters: Vec<T::AccountId> = proposal
        .votes
        .iter()
        .filter(|vote| vote.is_aye())
        .map(|vote| vote.who.clone())
        .collect();
    voters
}
```

Nothing is wrong at runtime; the annotation is simply detached from the call
that consumes it, which the project style forbids.

## Best practice

```rust
fn active_voters(proposal: &Proposal<T>) -> Vec<T::AccountId> {
    // ✅ The type lives on the collect() call itself.
    proposal
        .votes
        .iter()
        .filter(|vote| vote.is_aye())
        .map(|vote| vote.who.clone())
        .collect::<Vec<_>>()
}
```

`Vec<_>` is usually enough — the element type is inferred — so the turbofish
adds the container information exactly where it is needed.
