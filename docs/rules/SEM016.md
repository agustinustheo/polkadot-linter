# SEM016 - Missing `AuthorizeCall` in `CreateAuthorizedTransaction` Extension

> **Severity:** Warning · **Family:** semantic · **Engine:** compiler-backed (rustc driver) · **Rule name:** `missing-authorizecall-in-create-authorized-transaction`

## Description

Runtimes that use `#[pallet::authorize]` build their general (unsigned-but-authorized) transactions through the `frame_system::offchain::CreateAuthorizedTransaction` trait. Its `create_extension()` method assembles the transaction-extension pipeline that every transaction created this way will be validated with — typically a tuple mirroring the runtime's `TxExtension`, with the origin-restricting pieces swapped for authorization-friendly ones.

The critical piece of that tuple is `frame_system::AuthorizeCall::<Runtime>::new()`. This extension is what actually invokes the call's `#[pallet::authorize]` closure during transaction validation and charges the `#[pallet::weight_of_authorize]` weight. If `create_extension()` omits it, the transactions the runtime constructs — usually from offchain workers — are built with a pipeline that never runs the authorize step. Depending on the rest of the extension set, such transactions are either rejected at the pool (because nothing authorizes the unsigned origin) or, worse, accepted through some other permissive extension without the pallet's authorization checks ever executing. Either failure is silent at compile time: the code builds, and the bug only surfaces as offchain transactions that mysteriously never land or land unvetted.

Because this is a whole-program property — which trait is being implemented and which function is really being called — the rule is enforced by the rustc driver (it is listed in `COMPILER_BACKED_RULE_IDS` in `src/rules/mod.rs`), which resolves the trait to `frame_system::offchain::CreateAuthorizedTransaction` and the call to `frame_system::AuthorizeCall::new` through the type system rather than by name matching.

## What it detects

- An implementation of `frame_system::offchain::CreateAuthorizedTransaction` whose `create_extension()` body never constructs `frame_system::AuthorizeCall::new()`.
- The compiler-backed driver resolves both the implemented trait and the callee, so renamed imports or aliases are still recognized; a source-analysis (syn) fallback applies the same check for standalone file scans.
- Test files and `#[cfg(test)]` modules are skipped by the source-analysis fallback.

## What should be avoided

```rust
// ❌ the extension tuple never includes AuthorizeCall
impl<LocalCall> CreateAuthorizedTransaction<LocalCall> for Runtime
where
    RuntimeCall: From<LocalCall>,
{
    fn create_extension() -> Self::Extension {
        (
            frame_system::CheckNonZeroSender::<Runtime>::new(),
            frame_system::CheckSpecVersion::<Runtime>::new(),
            frame_system::CheckMortality::<Runtime>::from(generic::Era::immortal()),
            frame_system::CheckWeight::<Runtime>::new(),
        )
    }
}
```

Transactions built through this implementation skip the `#[pallet::authorize]` stage entirely, so the pallet's authorization logic is never consulted for them.

## Best practice

```rust
// ✅ AuthorizeCall routes the transaction through #[pallet::authorize]
impl<LocalCall> CreateAuthorizedTransaction<LocalCall> for Runtime
where
    RuntimeCall: From<LocalCall>,
{
    fn create_extension() -> Self::Extension {
        (
            frame_system::AuthorizeCall::<Runtime>::new(),
            frame_system::CheckNonZeroSender::<Runtime>::new(),
            frame_system::CheckSpecVersion::<Runtime>::new(),
            frame_system::CheckMortality::<Runtime>::from(generic::Era::immortal()),
            frame_system::CheckWeight::<Runtime>::new(),
        )
    }
}
```

With `AuthorizeCall` in the pipeline, every transaction created by the runtime runs the call's authorize closure and pays the declared authorization weight.
