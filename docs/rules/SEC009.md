# SEC009 - Raw Integer Arithmetic in Fallible Functions

> **Severity:** Advisory · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `raw-arithmetic-in-fallible`

## Description

Runtimes are compiled in release mode, where Rust's raw integer operators do not panic on overflow — they wrap silently (unless `overflow-checks` is enabled, in which case they panic, which is worse on a blockchain: a deterministic panic stalls every node at the same block). Either failure mode is unacceptable in state-transition logic. A balance that wraps from near-`u128::MAX` to a small number, or a counter that underflows to an enormous value, produces a state every honest node agrees on but nobody intended — funds can be minted or destroyed by arithmetic alone.

The Polkadot SDK convention is therefore to use explicit arithmetic in runtime code: `checked_*` operations that surface overflow as an error, or `saturating_*` operations that clamp at the numeric bounds when capping is acceptable. This rule enforces the convention precisely where it is cheapest to follow: inside functions that already return a `Result`. If the function can report errors, there is no excuse for wrapping silently — `a.checked_add(b).ok_or(Error::<T>::Overflow)?` costs one line.

The rule is deliberately flow-aware. Subtractions and divisions that are locally proven safe by a preceding guard are not reported, so idiomatic "check then compute" code stays clean while genuinely unguarded arithmetic is surfaced.

## What it detects

- Binary `+`, `-`, `*`, `/`, `%` expressions where both operands have compiler-resolved integer types, inside function bodies reachable from runtime entry points (public functions and FRAME hook implementations) **whose return type is fallible** (`Result`, including aliases such as `DispatchResult`).
- Reachability follows the local call graph, so helpers called from a fallible dispatchable are analyzed too.
- Exemptions derived from flow analysis on the current path:
  - a subtraction `a - b` guarded against underflow (e.g. inside `if a >= b { .. }`, in the `else` of `if a < b`, or after an early-exit guard that returns when `a < b`);
  - a division or remainder whose divisor is proven non-zero (guards such as `d != 0`, `d > 0`, `d >= 1`, a `match` arm on a positive integer literal, or an early exit on `d == 0`);
  - expressions on lines beginning with an attribute (e.g. weight annotations expanded by FRAME macros).
- One diagnostic is emitted per source line.

## What should be avoided

```rust
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::top_up())]
pub fn top_up(origin: OriginFor<T>, amount: u128) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ❌ wraps silently in release builds if the sum exceeds u128::MAX
    let new_total = Deposits::<T>::get(&who) + amount;

    Deposits::<T>::insert(&who, new_total);
    Ok(())
}
```

A caller who accumulates deposits near the type's maximum makes `new_total` wrap to a tiny value — the ledger silently loses funds, and every node agrees on the wrong number.

## Best practice

Option 1 — checked arithmetic, surfacing overflow as a dispatch error:

```rust
pub fn top_up(origin: OriginFor<T>, amount: u128) -> DispatchResult {
    let who = ensure_signed(origin)?;

    // ✅ overflow becomes an explicit, recoverable error
    let new_total = Deposits::<T>::get(&who)
        .checked_add(amount)
        .ok_or(Error::<T>::Overflow)?;

    Deposits::<T>::insert(&who, new_total);
    Ok(())
}
```

Option 2 — saturating arithmetic, when clamping at the bound is acceptable business logic:

```rust
// ✅ caps at u128::MAX instead of wrapping; no error path needed
let new_total = Deposits::<T>::get(&who).saturating_add(amount);
```

Guarded raw arithmetic is also accepted by the rule when the guard makes the operation provably safe:

```rust
// ✅ not reported: the subtraction cannot underflow here
ensure!(balance >= amount, Error::<T>::InsufficientBalance);
if balance >= amount {
    let remaining = balance - amount;
}
```
