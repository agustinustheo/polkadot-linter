# SEC002 - Debug Assertions Reachable from Runtime Entry Points

> **Severity:** Warning · **Family:** security · **Engine:** compiler-backed (rustc driver) · **Rule name:** `debug-assert-in-production`

## Description

`debug_assert!` (and its `_eq!`/`_ne!` variants) expands into a panic path that only exists in debug builds and is compiled out entirely in release builds. Neither behavior is what runtime code needs. In a debug-profile node, a failing `debug_assert!` panics — and a panic inside the runtime aborts block execution, which can stall a collator or, when nodes are built with different profiles, make them disagree about whether a block is valid. In a release-profile node, the check silently disappears, so the invariant it was meant to protect is simply not enforced where it matters most: production.

This is the same class of problem Libro's "Avoid Unwrap Usage Inside Runtime" chapter describes for `unwrap()`: runtime code must never contain a user-reachable panic. A condition worth asserting is either a real error case — which should return a `DispatchError` — or a defensive invariant, which FRAME expresses with the `defensive!`/`.defensive()` utilities that log loudly without differing between build profiles.

The compiler-backed check is reachability-aware: it does not merely grep for the macro, it starts from runtime entry points (dispatchables, hooks, and other externally reachable functions) and reports every `debug_assert!` that user input can actually reach — including ones in helper functions called from an extrinsic.

## What it detects

- `debug_assert!`, `debug_assert_eq!`, and `debug_assert_ne!` invocations inside any function body reachable from a runtime entry point (dispatchable calls, pallet hooks, and functions they transitively call).
- Occurrences are detected both in the expanded HIR and by scanning the authored source of reachable functions, so assertions hidden behind `cfg`-sensitive expansion are still reported. Each source line is reported once.

The diagnostic message is "`debug_assert!` expands into a debug-only panic path".

## What should be avoided

```rust
impl<T: Config> Pallet<T> {
    fn settle(who: &T::AccountId, amount: BalanceOf<T>) -> DispatchResult {
        let balance = Balances::<T>::get(who);
        debug_assert!(balance >= amount, "caller must have enough funds");
        Balances::<T>::insert(who, balance - amount);
        Ok(())
    }
}
```

In release builds the balance check vanishes and the subtraction can underflow; in debug builds a crafted call panics the node instead of returning an error.

## Best practice

Option 1 — return a proper error for user-reachable conditions:

```rust
fn settle(who: &T::AccountId, amount: BalanceOf<T>) -> DispatchResult {
    let balance = Balances::<T>::get(who);
    ensure!(balance >= amount, Error::<T>::InsufficientFunds);
    Balances::<T>::insert(who, balance.saturating_sub(amount));
    Ok(())
}
```

Option 2 — for internal invariants that should hold by construction, use FRAME's defensive utilities, which behave identically in all build profiles:

```rust
let balance = Balances::<T>::get(who)
    .checked_sub(&amount)
    .defensive_unwrap_or_default();
```

Either way, the invariant is enforced (or at least surfaced) in production instead of only in debug builds.
